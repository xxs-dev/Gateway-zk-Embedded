## 部署边界

使用 `production-install` 正式生命周期，不直接覆盖已固定哈希的在线脚本。候选继承原基线，仅变更 `bin/runtime-upgrade-guard.py`，`configWriteSet=[]`。旧脚本和审批对象先返回本地核验；生命周期保留旧文件和恢复事务。安装时暂停 kiosk 监护，完成后恢复。

成功提交后的回退需要基于当前基线创建新的反向升级事务，不能重放旧事务来强制覆盖更新后的基线。

实际安装事务 `BOOT_INVENTORY_20261015_V1` 已完成，基线 SHA256 为 `f5e495aea1acc5c8edb0e2fd9750eb076742bd1d71962b96ce588fa609418a35`，审批 SHA256 为 `b41ff530a81a8887919bf06b6c80a618540dcccdd384cde7baec4cd7cc2d97a2`。安装后检查确认原有三个业务进程各一个、8 项 kiosk 文件哈希/权限/所有者不变、无桌面进程、全屏和隔离正常。

## 首次重启失败与修正

第一次优化后重启 ID 为 `1824e55f-e1e9-489c-8977-19685294184a`。约 55.7 秒启动 EMS，但约 66 秒健康检查拒绝并保护性停服，最终 `FAILED_STOPPED`。此轮不是启动成功证据，也不能用 55.7 秒宣称优化验收通过。

失败原因为 `configured production excluded participant running`：当前基线明确排除 `gateway-health-watchdog.service`，但设备保留其 `multi-user.target.wants` 自启链接及失败重试。日志显示它于 25、39、51、61 秒反复进入启动检查，均被原有准入拒绝。健康采样撞上了未批准服务的启动中状态。减少检查耗时暴露了原有启用配置与准入配置不一致的时序问题。

修正前校验了基线哈希、该服务确实被排除、`MainPID=0`、服务已停止和唯一自启链接的准确目标；保留链接收据后执行 `systemctl disable gateway-health-watchdog.service`。未更改服务文件内容、恢复锁、拒绝条件或 baseline。硬件 watchdog、EMS kiosk 监护和全部允许的业务服务未禁用。

随后由本次启动固定哈希的 `production-boot-finish` 正式入口完成 `FAILED_STOPPED` 恢复，第二次尝试健康发布为 `FINISHED`，独立完整性/全屏/单进程/隔离检查通过。没有手工删除围栏或伪造健康证明。这次同启动周期的恢复属于显式恢复，不是开机自启通过；自启验收须依赖下一次整机重启。

失败日志在 `reboot/failed-boot-journal.log` 与 `reboot/excluded-units.log`；自启链接前后收据及恢复日志在 `watchdog-enablement/`。原始观察器未完成首屏测量而超时，失败日志保留；后续发现 `LC_ALL=C` 时中文窗口标题转换失败，须用固定的 `WM_CLASS` 和全屏尺寸匹配，不能匹配中文标题中的英文片段。修正后的匹配在实际设备上预检通过，并增加 SSH 通道短超时和失败状态即刻记录。
