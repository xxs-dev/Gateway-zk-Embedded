
# MQTT Driver

`MqttDriver` 是独立进程，不依赖 Modbus 串口。

同样适用于：

- `modbus_rtu`
- `modbus_tcp`
- `dlt645_2007`

职责：

- 从共享内存读取最新值
- 定时全量上传
- 主动拉取指定点位并上传
- 补发 `EventEngine` 写入 SQLite outbox 的告警和变位事件
- 发布运行状态到 `statusTopic`
- 订阅 MQTT 命令并写入共享待写队列
- 订阅 OTA 请求并执行升级脚本链路

配置文件：

- [mqtt-service.json](/D:/workspace/Embedded/Gateway-zk/config/runtime/apps/mqtt-service.json)

运行：

```bash
./build-aarch64/MqttDriver --app-config config/runtime/apps/mqtt-service.json
```

一次性主动拉取：

```bash
./build-aarch64/MqttDriver --app-config config/runtime/apps/mqtt-service.json --once --index 11000 --index 12000
```

当前状态：

- 已经拆成独立驱动进程
- 已经从共享内存读取数据
- 已经支持定时全量、事件 outbox 补发、一次性主动拉取
- 已经支持独立 `telemetryTopic / changeEventTopic / alarmTopic / statusTopic`
- MQTT 版本支持配置切换：`mqtt3` / `mqtt5`
- 已内置 MQTT 客户端实现，不依赖板子额外安装库
- 已支持订阅 `commandRequestTopic` 并将命令写入共享内存 `pendingWrites`
- 已支持发布命令回执到 `commandReplyTopic`
- 已支持接收 `otaRequestTopic` 并执行 OTA 脚本链路
- 已支持按阶段发布 `otaStatusTopic`
- 实时数据、全量快照、告警事件已包含 `machineCode / meterCode / pointCode`，消费端无需依赖本地 device 配置反查
- 告警和变位判断由独立 `EventEngine` 完成，`MqttDriver` 只负责从 outbox 补发和发送；这样 MQTT 断链时事件仍然按发生时间落盘

说明：

- `protocolVersion` 只允许 `mqtt3` 或 `mqtt5`
- 当前内置实现直接编译进驱动，不依赖 mosquitto/paho 等额外 MQTT 库
- 当前实现支持 TCP 直连、TLS、用户名密码、QoS0/QoS1、MQTT 3.1.1 和 MQTT 5
- 配置 `mqtt.tls.enabled=true` 或 broker 使用 `ssl://` / `tls://` / `mqtts://` 时启用 TLS；边端需要具备 OpenSSL 运行库 `libssl` / `libcrypto`
- `statusTopic` 当前用于发布驱动启动事件、全量快照事件和 OTA 过程状态
- `maxPayloadBytes` 当前用于实时数据 `telemetry / snapshot` 分片，默认 `49152` 字节，避免超过 broker 单条报文大小限制
- 实时页面消费直接订阅 `mqtt.telemetryTopic / mqtt.alarmTopic / mqtt.statusTopic`，Java 端不需要额外单独配置 `realtime.*Topic`；边端数据发送周期仍由 `mqttDriver` 的定时策略控制
- OTA 执行链依赖目标环境具备脚本、下载工具和校验命令；下载失败会按 `downloadRetryCount` 和 `downloadRetryBackoffMs` 重试

## MQTT TLS 生产接入

生产跨公网或不可信网络时，优先直接启用内置 TLS：

```json
"broker": "ssl://broker.example.com:8883",
"tls": {
  "enabled": true,
  "caFile": "/opt/modbus-gateway/config/runtime/tls/ca.crt",
  "certFile": "",
  "keyFile": "",
  "insecureSkipVerify": false
}
```

说明：

- `caFile` 为空时使用系统默认 CA 路径；嵌入式生产环境建议显式配置 CA 文件。
- `certFile` 和 `keyFile` 必须成对配置，用于 broker 要求客户端证书的双向 TLS。
- `insecureSkipVerify=true` 只允许临时联调使用，生产禁止开启。
- 如果目标系统 OpenSSL 运行库不可用，仍可使用 `mqtt-tls-tunnel@.service` 作为本机 stunnel 兜底方案。

运行依赖：

```sh
ldconfig -p | grep -E 'libssl|libcrypto'
```

内置 TLS 在运行时动态加载 OpenSSL，不需要把 OpenSSL 开发库交叉编译进程序；但边端系统必须存在可加载的 `libssl.so.1.1` / `libssl.so.3` 和 `libcrypto.so.1.1` / `libcrypto.so.3`。

已验证结果：

- 在边端 `192.168.22.12` 使用新编译的 `MqttDriver` 连接临时 TLS broker。
- broker 地址为 `ssl://192.168.22.11:8883`，CA 文件通过 `tls.caFile` 配置。
- TLS 握手协商到 `TLSv1.3`。
- 已完成 MQTT5 `CONNECT`、QoS1 `PUBLISH`、订阅 `SUBSCRIBE`、断开 `DISCONNECT`。
- 已回归 `tcp://192.168.22.102:1883` 明文 MQTT，确认现有非 TLS 配置不受影响。

限制：

- 已验证服务端证书校验模式。
- 双向 TLS 的 `certFile` / `keyFile` 已接入代码，但还需要带客户端证书校验的真实 broker 做现场联调。

## MQTT 离线缓冲

主站或 broker 断链时，`MqttDriver` 按数据类型分开缓存：

- 实时数据写入预分配 ring 文件：`/opt/modbus-gateway/data/mqtt-spool/realtime_ring.dat`
- 告警、变位、OTA 状态写入 SQLite outbox：`/opt/modbus-gateway/data/mqtt_event_outbox.db`

连接恢复后，驱动每次发送前会优先补发 SQLite 关键事件，再补发实时 ring 数据，最后发送当前新消息。

字段说明：

- `enabled`：是否启用断链缓冲。
- `mode`：当前使用 `ring`。
- `realtimeFile`：实时数据 ring 文件。
- `realtimeFileSizeBytes`：ring 文件大小，当前建议 1GB。
- `maxRealtimeMessageBytes`：单条实时消息最大大小，当前建议 4MB。
- `replayBatchSize`：实时 ring 每轮最多补传条数。
- `eventOutbox.sqlitePath`：关键事件 outbox 数据库路径。
- `eventOutbox.retentionMonths`：已发送事件自然月保留数，默认 12。
- `eventOutbox.cleanupIntervalHours`：清理检查间隔。
- `eventOutbox.replayBatchSize`：关键事件每轮最多补传条数。

详细设计见 [断链缓存补传设计.md](D:/workspace/Embedded/Gateway-zk/doc/断链缓存补传设计.md)。

实时数据分片：

当单次 `telemetry / snapshot` 预计超过 `mqtt.maxPayloadBytes` 时，`MqttDriver` 会自动拆成多条 MQTT 消息，仍发布到 `telemetryTopic`。

```json
{
  "type": "snapshot",
  "machineCode": "GW0001",
  "chunked": true,
  "chunkId": "1776906000000-1",
  "chunkIndex": 1,
  "chunkCount": 3,
  "meters": [
    {
      "meterCode": "TTYSP1_SLAVE0001",
      "values": [
        {
          "index": 31101,
          "pointCode": "reg_1",
          "value": 123,
          "quality": 1,
          "ts": 1776906000000,
          "expireAt": 1776906600000,
          "stale": false
        }
      ]
    }
  ]
}
```

字段说明：

- `chunked=true`：表示这是分片实时数据；未分片消息可没有该字段。
- `chunkId`：同一次全量或主动拉取的分片批次 ID。
- `chunkIndex`：当前第几片，从 `1` 开始。
- `chunkCount`：本批次总片数。
- `meters`：本片包含的仪表和点值，结构与未分片实时数据一致。

平台处理建议：

- 实时页面可以收到一片就刷新一片，不必等待所有分片到齐。
- 如果平台需要恢复完整快照，按 `machineCode + chunkId` 聚合，收到 `chunkCount` 片后再合并。
- 分片可能因网络和补传乱序到达，不能依赖 MQTT 接收顺序。
- `maxPayloadBytes` 是分片目标上限，不建议配置太接近 broker 极限；broker 限制 50KB 时建议保留默认 `49152` 或更小。

样例文件：

- [mqtt_telemetry_chunk_example.json](/D:/workspace/Embedded/Gateway-zk/config/samples/messages/mqtt_telemetry_chunk_example.json)

## 命令下发协议

配置中的基础 topic：

```text
edge/command/request
edge/command/reply
```

运行时实际 topic：

```text
edge/command/request/<machineCode>
edge/command/reply/<machineCode>
```

推荐请求 JSON：

```json
{
  "cmdId": "CMD2026041415300001",
  "machineCode": "GW0001",
  "meterCode": "SLAVE0001",
  "index": 11001,
  "pointCode": "reg_1",
  "value": 1,
  "source": "mqtt",
  "ts": 1776155909818
}
```

推荐回执 JSON（实际字段，见 `config/samples/messages/mqtt_command_result_*_example.json`）：

```json
{
  "cmdId": "CMD2026041520000001",
  "machineCode": "GW0001",
  "meterCode": "SLAVE0001",
  "pointCode": "reg_1",
  "index": 11001,
  "value": 1,
  "success": true,
  "outcome": "succeeded",
  "final": true,
  "message": "ok",
  "stage": "writeback-succeeded",
  "requestedAt": 1776157199800,
  "acceptedAt": 1776157199810,
  "writeStartedAt": 1776157199830,
  "writeCompletedAt": 1776157200000,
  "queueDelayMs": 20,
  "deviceWriteMs": 170,
  "edgeElapsedMs": 190,
  "totalElapsedMs": 190,
  "verifyAttempted": true,
  "verifyPassed": true,
  "highPriority": false,
  "ts": 1776157200000
}
```

回执字段说明：

- `success`：仅在写入确认成功时为 `true`。
- `outcome`：控制结果三态，决定能否重发：`succeeded`（已确认成功）/ `failed`（确定没有生效：设备明确拒绝、
  请求未发出、排队过期、入口拒绝）/ `unknown`（**设备可能已经执行**）。`unknown` 的回执不得自动重发，也不得换新
  `cmdId` 重试；应先读回点值确认，或以同一 `cmdId` 重发查询（不会再次执行）。`success=false` 时须看 `outcome`。
- `stage`：保留原因，`message` 保留执行器的原始说明（如 `verify failed: wrote 7, read back 5`）：
  - 成功：`writeback-succeeded`、`local-parameter-committed`（EMS 虚拟参数）、`mailbox-committed`（AGC/AVC 信箱）。
  - `failed`：`writeback-failed`（设备异常应答等确定失败，或请求未发出）、`expired`（排队超过
    `memoryStore.pendingWriteMaxAgeMs`，按单调时钟计、不受系统改时影响，未下发）、`control-rejected`（授权拒绝：
    功率控制权不符、EMS 就地模式或模式切换撤销平台命令、AGC/AVC 信箱未授权本入口（`agcAvc.commandMailbox`）、
    信箱请求高优先级或 index 未在 `agcAvc` 中配置；载荷 `source` 不能改变授权结果）、
    `writeback-skipped`、`rejected`（入口校验拒绝）、`rate-limited`（超过 `commandRateMaxPerWindow`）。
  - `unknown`：`writeback-mismatch`（**反馈不一致**：设备已接受写入，但回读或反馈显示另一值——这不等于“设备没有执行”，
    设备可能已动作或部分动作，不得据此自动重发）、`writeback-timeout`（已发出但没有确定应答；也用于边端等待结果超时的
    非最终回执）、`writeback-unconfirmed`（账本里已预留派发但没有记录结果：可能仍在执行，也可能执行中进程中断；
    不会再次派发）、`duplicate`、`duplicate-in-flight`。
- `final`：`false` 表示之后同一 `cmdId` 还可能再来一次回执：边端等待结果超时（`stage=writeback-timeout`）、同一 `cmdId`
  仍在执行（`duplicate-in-flight`）、重放到只有预留没有结果的记录（`writeback-unconfirmed`）。边端继续等待一个等待时长，
  拿到最终结果就以同一 `cmdId` 发 `final=true` 的回执，否则发 `final=true`、`outcome=unknown`（原因保持不变）的回执结束。
- 一致性：同一 `cmdId` 的首次回执、共享内存回执、SQLite 去重账本记录、同 `cmdId` 重放与晚到回执给出同一结果
  （`outcome`、`stage`、`message` 一致，进程重启后从账本重放也一致）。唯一允许的变化是非最终的 `unknown`
  被晚到的最终结果取代；已给出的 `succeeded`/`failed` 不会再变，账本里的最终记录（含 `writeback-mismatch`、
  `writeback-timeout`）也不会再变。
- 时间字段：`requestedAt`（命令 ts，缺省为接收时间）、`acceptedAt`、`writeStartedAt`、`writeCompletedAt`、
  `queueDelayMs`、`deviceWriteMs`、`edgeElapsedMs`、`totalElapsedMs`；`ts` 为回执时间。

结果等待：实际等待时长 = max(`mqttDriver.controlResultWaitTimeoutMs`，各设备 `memoryStore.pendingWriteMaxAgeMs` + 2000 ms)，
保证超时回执发出时排队命令已不可能再开始执行（默认 5000 / 10000 → 12000 ms）。等待按实际经过时间计：
系统时间跳变（≥1 s）时等待截止时刻随之平移，前跳不会提前发超时回执，后跳也不会把回执推迟一个跳变量。

同一 `cmdId` 重复下发：

- 仍在执行或等待结果中：不重复执行，回执 `stage=duplicate-in-flight`、`outcome=unknown`、`final=false`，最终结果随后发出；
  同一 `cmdId` 但 `index`/`value` 不同则拒绝。
- 已有最终结果：物理写点由 SQLite 去重账本重放原结果（每个 `cmdId` 最多派发一次）；EMS 虚拟参数在
  `commandDedupTtlMs` 内重放原结果，取不到原结果时回执 `stage=duplicate`、`outcome=unknown`。
- 限流（`rate-limited`）与重复（`duplicate*`）的回执相互独立。

当前 OTA 执行链：

```text
OTA请求 -> 参数校验 -> accepted回执 -> 下载 -> 校验 -> applyScript -> 失败时rollbackScript -> 阶段状态上报
```

限制：

- 当前已写出 `current_version.txt` 与 `upgrade_history.log`，并按 `retentionCount` 清理旧下载包；进程级重启编排仍未实现
- `upgradeTimeoutSec` 当前已在下载后和校验后做阶段超时检查
- `storage.provider=minio` 当前已支持按 `publicBaseUrl` 或 `endpoint/bucket/basePath` 组合生成下载地址


## OTA 脚本协议

当前 OTA 执行器调用脚本时，参数顺序固定如下：

```text
1. artifactPath
2. version
3. jobId
4. backupDir
5. stagingDir
```

示例：

```bash
sh /opt/modbus-gateway/bin/ota-apply.sh   /opt/modbus-gateway/ota/downloads/1.2.3.tar.gz   1.2.3   OTA2026041519000001   /opt/modbus-gateway/ota/backup   /opt/modbus-gateway/ota/staging
```

参考脚本：

- [ota-apply.sh](/D:/workspace/Embedded/Gateway-zk/deploy/ota-apply.sh)
- [ota-rollback.sh](/D:/workspace/Embedded/Gateway-zk/deploy/ota-rollback.sh)

脚本约定：

- 返回 `0` 表示成功
- 非 `0` 表示失败，失败时 OTA 服务会尝试调用 `rollbackScript`
- 当前 OTA 服务不解析脚本 stdout/stderr，只依据退出码判断结果
