# RS-485 收发方向逐串口核验（只读）

本文用于逐个串口确认：RS-485 收发器在发送和接收之间靠什么切换方向，以及边端是否需要打开设备配置里的 `protocol.transport.rs485`。

全部步骤都是只读的：不修改配置、不重启服务、不发控制命令，也不执行 `TIOCSRS485`。

## 1. 为什么不能用"通信正常"作为依据

以下几种机制都会让轮询看起来一切正常，但它们对配置的要求互不相同：

- 收发器带自动方向切换，例如自动方向收发器芯片，或由 TXD 经三极管驱动 DE 的电路。这种情况软件什么都不用做。
- 设备树里写了 `linux,rs485-enabled-at-boot-time`，内核在开机时就接管了 RTS 方向控制，与边端配置无关。
- 内核里的 RS-485 设置是之前某个进程设置后留下的。它一直保留到重启，`transport.rs485.enabled=false` 不会去清除它。
- RTS 的上电默认电平或打开串口时的电平，恰好让收发器处在"能收"或"能发"的一侧。
- 收发切换的时序余量很小，只在某些波特率、设备应答时间或线缆长度下才出错。偶发的超时和 CRC 错会被读重试掩盖，看起来像"偶尔掉包"。

所以结论必须来自硬件资料、设备树和内核当前状态（第 3–6 节）；可选的波形观测见第 7 节。轮询结果只能当旁证。

## 2. 找到每一路的实际设备

`ttySP*` 是板级命名，先找到它对应的内核 tty：

```sh
ls -l /dev/ttySP*                         # 符号链接或设备号
readlink -f /dev/ttySP1                   # 例如 /dev/ttyS1
```

下面用 `N` 表示该路对应的 `ttySN`：

```sh
ls /sys/class/tty/ttySN/
cat /sys/class/tty/ttySN/type /sys/class/tty/ttySN/iomem_base /sys/class/tty/ttySN/irq 2>/dev/null
basename "$(readlink -f /sys/class/tty/ttySN/device/driver)"   # 串口驱动名（8250/DW 系列、厂家 BSP 驱动等）
readlink -f /sys/class/tty/ttySN/device/of_node                 # 对应的设备树节点
```

`of_node` 指向 `/sys/firmware/devicetree/base/...` 下的节点目录，是 tty 与设备树节点最直接的对应关系。`iomem_base` 应当与节点的单元地址一致。

## 3. 硬件资料（决定性依据）

逐路查板卡原理图或硬件手册，记录：

- 收发器型号；
- DE 与 /RE 的连接方式；
- 是否经过反相器；
- 接在哪个 SoC 引脚上。

| DE / RE 的接法 | 含义 |
| --- | --- |
| 自动方向收发器，或 TXD 经三极管/逻辑电路驱动 DE | 硬件自动收发。`transport.rs485` 保持关闭 |
| 接在该 UART 的 RTS 引脚（可能经反相器） | 需要有人控制 RTS：内核 RS-485（设备树开机启用，或 `transport.rs485.enabled=true`） |
| 接普通 GPIO | 需要设备树里的 `rts-gpios` 等由内核驱动该 GPIO，或其他方案。不在 `transport.rs485` 的能力范围内，交给硬件方确认 |
| DE 恒为有效、/RE 恒为有效，或接法不明 | 不改配置，先补硬件资料 |

RTS 极性：

- `rtsOnSend`/`rtsAfterSend` 是内核的逻辑电平：`true` 表示发送期间（或发送后）RTS 有效。
- 常见的 16550 兼容 UART（包括 8250/DW 系列）里，RTS 有效时 nRTS 引脚输出低电平。具体以 SoC 手册为准。
- 举例：DE 高电平有效、且直接接在 nRTS 上，发送时就需要 RTS 无效，即 `rtsOnSend=false`、`rtsAfterSend=true`；中间有反相器则相反。
- 极性只能按原理图确定，不能试出来。

## 4. 设备树（只读查看）

```sh
NODE=$(readlink -f /sys/class/tty/ttySN/device/of_node)
ls "$NODE"                                         # 布尔属性以空文件出现
cat "$NODE/compatible"; echo; cat "$NODE/status"; echo
for p in linux,rs485-enabled-at-boot-time rs485-rts-active-low rs485-rts-active-high rs485-rx-during-tx; do
  [ -e "$NODE/$p" ] && echo "$p: present"
done
[ -e "$NODE/rs485-rts-delay" ] && hexdump -C "$NODE/rs485-rts-delay"   # 两个大端 u32：发送前、发送后，单位 ms
ls "$NODE" | grep -i -E 'gpio|rs485|rts'            # rts-gpios、rs485-term-gpios，以及厂家自定义属性
```

需要整棵树时（只读，需要 `dtc`）：

```sh
dtc -I fs -O dts /sys/firmware/devicetree/base 2>/dev/null | less
```

记录该节点下所有与 RS-485、RTS、GPIO 有关的属性，包括厂家 BSP 自定义的属性。

- 有 `linux,rs485-enabled-at-boot-time`：内核开机就启用了 RS-485 方向控制，极性和延时来自设备树。
- 没有：内核默认不控制方向。

## 5. 内核与驱动能力

```sh
uname -r
zcat /proc/config.gz 2>/dev/null | grep -E 'CONFIG_SERIAL_(8250|OF_PLATFORM|SUNXI)' \
  || grep -E 'CONFIG_SERIAL_(8250|OF_PLATFORM|SUNXI)' "/boot/config-$(uname -r)" 2>/dev/null
grep -i rs485 /proc/kallsyms | awk '{print $3}' | sort -u     # root；只看符号名
```

- `/proc/kallsyms` 里出现该驱动的 `*_rs485_config` 符号，或 8250 的 `serial8250_em485_*`，说明内核里有 RS-485 方向控制代码。这只是旁证；驱动是否支持某个端口，最终以内核/BSP 源码或厂家说明为准。
- 驱动没有 RS-485 支持时，`TIOCSRS485` 返回 `Inappropriate ioctl for device`。边端打开串口时会因此报错退出，不会降级运行。

## 6. 当前内核状态（只做 TIOCGRS485）

本节只读取状态，不写任何设置。

运行时机：

- 最好在该路驱动服务正在运行、串口已被打开时执行。这时再打开一次不会改变 RTS/DTR。
- 服务停止时，第一次打开串口会让多数 UART 驱动置位 RTS/DTR。若 DE 接在 RTS 上，可能短暂把收发器切到发送。所以服务停止时不要执行，或只在维护窗口执行。
- 需要 root：边端驱动对串口设置了 `TIOCEXCL`。

```sh
python3 -c '
import fcntl, os, struct, sys
fd = os.open(sys.argv[1], os.O_RDONLY | os.O_NOCTTY | os.O_NONBLOCK)
buf = bytearray(32)
try:
    fcntl.ioctl(fd, 0x542E, buf)   # TIOCGRS485, read only
except OSError as e:
    print("TIOCGRS485 error:", e.errno, os.strerror(e.errno)); sys.exit(0)
flags, before, after = struct.unpack("III", bytes(buf[:12]))
print("flags=0x%x enabled=%d rtsOnSend=%d rtsAfterSend=%d rxDuringTx=%d terminate=%d delayBefore=%d delayAfter=%d" % (
    flags, flags & 1, (flags >> 1) & 1, (flags >> 2) & 1, (flags >> 4) & 1, (flags >> 5) & 1, before, after))
' /dev/ttySP1
```

结果解读：

| 结果 | 含义 |
| --- | --- |
| `error: 25 Inappropriate ioctl for device` | 不是带 RS-485 接口的 UART（例如 USB 转串口、pty），内核不可能控制方向，只能靠硬件 |
| `enabled=1` | 内核 RS-485 当前已生效（来自设备树开机设置，或此前有进程设置过）。记录极性和延时，与原理图核对 |
| `enabled=0` | 内核当前不控制方向。不能说明驱动是否支持：没有 RS-485 支持的驱动读取时通常也返回全 0 |

串口统计与线路状态（不打开设备）：

```sh
ls /proc/tty/driver/
cat /proc/tty/driver/serial 2>/dev/null     # 8250 系列：每口的 uart 类型、地址、tx/rx 计数和 RTS|DTR 等线路状态
```

厂家驱动可能使用其他文件名，按 `ls` 的结果读取对应文件。tx/rx 计数只能说明有收发，不能说明方向机制。

## 7. 可选：轮询期间观测波形

能直接证明方向机制的，只有现场观测：在只读轮询期间（不发控制命令），用示波器或逻辑分析仪同时测 TXD、DE（/RE）和 RTS 引脚，确认：

- DE 是否在每帧发送前有效、发送结束后释放；
- 由哪个信号驱动；
- 释放时刻与最后一个停止位之间的余量。

观测结果填入记录表的"依据"列。

## 8. 结论与配置

| 依据 | 配置 |
| --- | --- |
| 硬件自动收发 | `transport.rs485` 保持关闭（默认值） |
| DE 接 RTS，且设备树已开机启用、极性和延时与原理图一致 | 可以保持关闭（内核已负责）。也可以打开，让驱动在每次打开串口时设置并读回核对；选哪种需用户决定 |
| DE 接 RTS，内核未启用，驱动支持 RS-485 | 需要 `enabled=true`，极性按第 3 节、延时按收发器和设备应答时间确定。在维护窗口改配置，用第 7 节确认 |
| DE 接 GPIO、接法不明、驱动不支持 | 不改配置，交给硬件方 |

没有现场依据时，不修改生产配置。
