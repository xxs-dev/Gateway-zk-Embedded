# 边端业务健康看门狗

## 1. 目标和边界

`gateway-health-watchdog.service` 用于处理“进程仍由 systemd 管理，但业务服务没有完整恢复”的场景。它独立于 `gateway-services.service` 运行，每次根据当前配置重新生成目标服务清单，不维护另一份固定驱动列表。

它与硬件看门狗分工如下：

| 机制 | 处理范围 |
| --- | --- |
| 各实例的 `Restart=always` | 单进程意外退出后的首次快速拉起 |
| 业务健康看门狗 | 目标服务持续 inactive、配置应用后的服务缺失 |
| systemd 硬件看门狗 | 内核、PID1 或整机失去调度能力 |

业务看门狗不判断设备通信质量，不会因为某个 Modbus 从站离线而重启进程。协议在线状态、退避和恢复仍由对应采集驱动负责。

## 2. 恢复层级

默认每 10 秒检查一次，连续 3 次失败后执行恢复：

1. 采集、计算、事件、转发、画面、SystemMonitor 或 MQTT 实例缺失时，先清除该 unit 的 systemd start-limit，再只重启缺失实例。局部恢复不停止其他服务，也不删除共享内存。
2. 只有 `gateway-services.service` 启动器本身缺失时，才重新启动该 unit，并按当前配置重建完整运行态。恢复路径使用 `start`，不经过会写入人工停服标记的 `ExecStop`。
3. MQTT、SystemMonitor 或启动器等关键服务局部恢复连续失败 3 次后，才允许请求整机重启。普通采集实例恢复失败不会触发整机重启。
4. 蜂窝拨号和路由切换服务不纳入业务进程恢复，防止健康检查主动中断远程维护链路。
5. 整机重启设置 30 分钟冷却，并限制为 24 小时最多 2 次。

配置解析失败、目标服务清单为空或 unit 名称非法时，只写 degraded 状态，禁止整机重启。

## 3. 默认参数

参数文件为 `/etc/default/gateway-health-watchdog`：

```text
WATCHDOG_CHECK_INTERVAL_SEC=10
WATCHDOG_STARTUP_GRACE_SEC=60
WATCHDOG_FAILURE_THRESHOLD=3
WATCHDOG_RECOVERY_VERIFY_SEC=30
WATCHDOG_RECOVERY_COOLDOWN_SEC=120
WATCHDOG_APPLYING_STALE_SEC=900
WATCHDOG_REBOOT_FAILURE_THRESHOLD=3
WATCHDOG_RECOVERY_WINDOW_SEC=900
WATCHDOG_REBOOT_COOLDOWN_SEC=1800
WATCHDOG_REBOOT_RATE_WINDOW_SEC=86400
WATCHDOG_MAX_REBOOTS_PER_WINDOW=2
```

不要为了现场观察把恢复复查时间长期压缩到 5 秒以下。单个实例通常可在数秒内恢复；只有启动器本身失败时才执行完整运行态重建，期间会受到串口超时、共享内存释放和 Qt 画面启动影响。

## 4. 抑制标记

以下标记用于区分人工操作和真实故障：

| 文件 | 含义 |
| --- | --- |
| `/run/gateway-health-watchdog/manual-stop` | 运维人员明确停止网关，不允许自动拉起 |
| `/run/gateway-health-watchdog/applying` | 正在应用配置或重建运行态，暂不判故障 |

标记包含创建进程、boot ID 和单调启动时间。`applying` 的创建进程消失、跨 boot 或超过 `WATCHDOG_APPLYING_STALE_SEC` 时会自动清理，避免升级进程被强杀后永久 suspended；`manual-stop` 只会在明确 start/apply 后清除，不自动过期。

人工停服必须使用 `gateway-services.sh stop` 或 `systemctl stop gateway-services.service`。配置应用和 OTA 使用 `reload-or-restart`，不会把恢复过程误记为人工停服。不要手工创建这两个标记。

## 5. 状态和日志

查看服务与结构化状态：

```bash
systemctl status gateway-health-watchdog.service --no-pager
journalctl -u gateway-health-watchdog.service -n 100 --no-pager
cat /var/lib/modbus-gateway/watchdog/status.json
```

状态文件包含检查时间、健康状态、最近动作、缺失服务、连续失败次数和冷却截止时间。常见动作：

| `lastAction` | 含义 |
| --- | --- |
| `none` | 本轮健康，不需要恢复 |
| `restart-inactive-units` | 正在局部重启缺失实例 |
| `units-restarted` | 缺失实例已恢复 |
| `start-gateway-services` | 启动器自身缺失，正在重建运行态 |
| `gateway-started` | 启动器和运行态已恢复 |
| `manual-stop` | 人工停服抑制中 |
| `configuration-applying` | 配置应用抑制中 |
| `reboot-requested` | 已通过限流检查并请求整机重启 |

## 6. 部署与回滚

工厂安装脚本会安装并 enable 看门狗，只有 `START_SERVICES=1` 时才启动。手工安装命令：

```bash
install -m 0755 deploy/gateway-health-watchdog.sh /opt/modbus-gateway/bin/gateway-health-watchdog.sh
install -m 0644 deploy/gateway-health-watchdog.service /etc/systemd/system/gateway-health-watchdog.service
install -m 0644 deploy/gateway-health-watchdog.default /etc/default/gateway-health-watchdog
systemctl daemon-reload
systemctl enable --now gateway-health-watchdog.service
```

回滚时先停看门狗，再恢复旧运行脚本：

```bash
systemctl disable --now gateway-health-watchdog.service
rm -f /etc/systemd/system/gateway-health-watchdog.service
rm -f /etc/default/gateway-health-watchdog
rm -f /opt/modbus-gateway/bin/gateway-health-watchdog.sh
systemctl daemon-reload
```

## 7. 上线约束

普通子服务恢复不会重建共享内存。只有启动器自身缺失、明确配置 apply 或完整升级时才重建共享内存。执行完整升级前必须确认同一设备上的采集驱动、计算服务、SystemMonitor、MQTT 和 `KY-EMS` 来自同一兼容包。禁止改变设备驱动在服务清单中的既有启动顺序，避免存量混合版本由不同进程抢先创建不兼容的共享内存段。

OTA 白名单包含看门狗脚本、unit 和默认参数；OTA 与回滚全过程都会写入 `applying`。`gateway-services.service` 已运行时通过 `reload-or-restart` 应用，避免先执行 `ExecStop` 产生错误的人工停服标记。

建议先在测试机执行：

```bash
sh tools/gateway_health_watchdog_test.sh
sh tools/gateway_services_watchdog_lifecycle_test.sh
/opt/modbus-gateway/bin/production-smoke-test.sh
```

## 8. 192.168.22.16 验证记录

2026-09-05 在 `192.168.22.16` 完成以下验证：

- 正常运行状态：看门狗输出 healthy。
- 人工停服：超过检测阈值后仍保持 `suspended/manual-stop`，未误拉起。
- 配置应用：`applying` 存在时保持 `suspended/configuration-applying`。
- 普通采集故障：停止 `modbus-rtu@device_modbusTCP_22_8.service` 后，仅该实例被重启，`gateway-services.service` 激活时间戳未变化，`KY-EMS` 保持 active。
- 关键服务故障：停止 `mqtt-driver@mqtt-service.service` 后只恢复该 MQTT 实例，约 4 秒完成；`gateway-services.service`、SystemMonitor、采集服务、`KY-EMS` 和全部共享内存 inode 均未变化。
- 配置应用残留：持有 `applying` 的进程退出后，标记约 1 秒被识别为失效并清理，随后恢复缺失实例。
- 信号中断清理：看门狗在生成目标 unit 清单期间收到 `SIGTERM` 时，会删除本进程的 `desired-units.<pid>` 临时文件；用于 `flock` 的 `recovery.lock` 保留。
- 最终冒烟：`pass=79`、`warn=3`、`fail=0`；告警为 IMEI 为空、MQTT 配置权限过宽和未启用主动 MQTT 连接探测，均非本次变更引入。

测试期间确认：失败冷却、启动宽限和配置应用租约必须使用单调时间；服务启动顺序不能为了维护优先而改变，正确做法是保持配置顺序并在单实例启动失败后继续处理后续服务。生产老设备必须按单机灰度执行，先备份、再替换、记录原平台 MQTT 断链时长并分别注入采集实例和 MQTT 单实例故障，禁止多台设备同时注入。

## 9. 老设备灰度记录

2026-09-05 按 `COMM202600092`、`COMM202600091` 的顺序完成单机灰度，两台均为 systemd 245 和共享内存 v9；未同时执行故障注入。

- `COMM202600092`：MqttDriver 切换后在同一秒恢复原 broker 的两条连接，MqttForwarder 切换耗时 484 ms。默认 `10 秒 × 3 次` 下，`ttySP8` 人工停止后 22.833 秒局部恢复，仅该实例的共享内存 inode 改变。临时使用 `1 秒 × 1 次` 验证 MQTT 局部恢复时耗时 524 ms，两条 socket 均恢复，其他服务和共享内存不变。正式参数已恢复默认值。
- `COMM202600091`：保留 `peidian` 旧平台 legacy 格式和 1 秒上传周期。MqttForwarder 切换至 active 用时 363 ms，两条 broker socket 全部恢复用时 972 ms；持续观察一分钟，两条 socket 的 `bytes_sent` 均增长，Full 上传成功时间持续推进。默认参数下，`ttySP2` 人工停止后 30.529 秒局部恢复，仅自身共享内存 inode 改变。临时加速验证 Forwarder 恢复时，active 用时 743 ms、两条 socket 恢复用时 1.324 秒，其他服务和共享内存不变。正式参数已恢复默认值。
- 两台最终目标服务均为 active，核心 unit 的 `NRestarts=0`，运行目录中只保留正常的 `recovery.lock`。
- `COMM202600092` 的既有 Full 清单声明包含 `KY-EMS`，但设备是普通 gateway 模式且未安装该文件，导致旧冒烟脚本产生一项清单一致性失败。该问题不影响本次看门狗和 MQTT 灰度结论，但后续重做该设备项目包时应改用与实际组件一致的 project 清单。

OTA 异步重启使用 PID 所有权交接：父进程启动重启子进程后，通过临时文件加原子重命名把 `applying` 标记交给子 PID；子进程退出时只删除仍属于自己的标记，避免看门狗提前恢复或旧任务误删后来任务的标记。
