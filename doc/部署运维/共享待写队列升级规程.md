# 共享待写队列升级规程

适用于升级或回滚"往共享内存待写队列提交命令"和"从队列取命令执行"的程序，典型场景是本版本把待写命令有效期改为单调时钟（待写槽新增 `acceptedMonotonicMs`）。共享内存仍是 v11，段大小和字段偏移不变，不做离线迁移，也不删除共享内存段。

原则：

- 关联服务统一维护窗口，只停、只换、只启动下文列出的写入方和驱动；不是整机业务服务一起重启，也不重启网关。
- EasyTier、4G、网络服务不动。
- 先暂停平台、本机和 EMS 策略的写入入口，核清在途命令，再一起升级生产者和消费者。
- 旧命令只有确认"未执行、已过期"（回执 `stage=expired`）才允许重新提交，而且必须用新 `cmdId`。
- 结果未知的命令先核验设备实际状态，不要求平台一律重发。

## 1. 兼容性实测结论

`tools/shm_pending_write_mix_check.sh` 用本版本和旧版本分别编译的 `shm_pending_write_mix`，对同一个共享内存段实测，消费方走真实的 `GatewayDaemon` 写回路径，执行器只记录、不碰设备。已对 `dabb8fd`（realese1.0）和 `29f5068` 两个基线逐项通过：

| 情形 | 结果 |
| --- | --- |
| 旧生产者 → 新驱动 | 旧版本写的槽 `occupied=1`。新驱动不读取其中的空隙字节，命令判过期、不下发，回执 `stage=expired` |
| 旧生产者，但空隙里恰好是"看起来新鲜"的值或随机值 | 同上：判过期、不下发。修复前的第二轮代码在这种情况下会执行该命令，现已修复 |
| 新生产者 → 旧驱动（回滚） | 新版本写的槽 `occupied=2`。旧驱动只判断 `occupied` 是否非 0，所以照常读取，按原来的墙钟逻辑执行或判过期 |
| 升级途中段内留有旧命令 | 新驱动把旧命令判过期并写回执；同一时刻入队的新命令正常执行 |
| 回滚后段内留有新命令，且被只认领其他点位的旧驱动搬移过 | 旧驱动搬移时保留空隙字节（x86 GCC 13 与生产 GCC 6.3 aarch64 -O3 均实测），重新升级后新驱动按原单调戳正确判断新鲜或过期 |
| 段由任一版本创建、另一版本附着 | 版本号都是 11，双方都能正常附着、入队和执行 |

补充说明：

- 实测旧版本（两种编译器）入队时空隙一律写 0。
- 本版本的判断不依赖这一点：只有 `occupied=2` 的槽才使用单调戳。
- 现有迁移机制的回归在独立 PID 命名空间里通过：`memory_point_store_migration`、`memory_point_store_v11_migration`、`memory_point_store_shm11`。v10 段仍被拒绝；队列非空时迁移仍被拒绝。

混跑在两个方向上都安全（不会执行过期命令），但不是受支持的运行状态，必须在同一个窗口内完成升级或回滚。

### 写回回执混跑

写回回执槽的 `success` 字节各位含义：`0x01` 成功，`0x02` 高优先级，`0x04` 结果未知，`0x08` 反馈不一致（写入时与 `0x04` 一起置位）。本版本写的回执槽另标 `occupied=2`；旧版本写的是 `occupied=1`，各版本读取方都只判断非 0。

读取方共有三条路径：MQTT 回执、`pointctl result/results`、直连维护回执查询。每个版本内，这三条路径共用同一套解码和同一个 outcome 表达式：

- dabb8fd：只有 `success` 和 `stage`，没有 outcome。
- 29f5068：`success ? succeeded : (0x04 ? unknown : failed)`，回执一律为最终回执。
- 本版本：`writeback_outcome.hpp`。

按 cmdId 查找、按点位取最近回执两条解码路径都已实测；另外用 29f5068 与本版本真实的 `pointctl` 端到端核对过。

| 本版本写入的回执 | dabb8fd 读取方 | 29f5068 读取方 | 本版本读取方 |
| --- | --- | --- | --- |
| `writeback-mismatch`（`0x0C`） | `success=false`，stage 原样，无 outcome | unknown | unknown |
| `writeback-unconfirmed`（`0x04`） | `success=false` | unknown（但作为最终回执） | unknown，非最终 |
| `writeback-timeout`（`0x04`） | `success=false` | unknown | unknown |
| `writeback-failed` | `success=false` | failed | failed |
| `writeback-succeeded` | `success=true` | succeeded | succeeded |

| 旧版本（dabb8fd / 29f5068）写入的回执 | 本版本读取方 |
| --- | --- |
| `writeback-failed`：dabb8fd 把 Modbus 超时记为此 stage，两个基线把回读不一致也记为此 stage | unknown，stage 原样保留（修复前读成 failed，平台可能据此换新 cmdId 重发） |
| `writeback-timeout` | unknown |
| `expired`、`control-rejected`、`rejected`、`rate-limited`、`writeback-skipped`、`malformed-rejected`、`owner-died` | failed（这些 stage 都没有到达设备） |
| `writeback-succeeded` | succeeded |

结论：本版本写的"反馈不一致/未确认/超时"回执，任何读取方都不会读成成功，29f5068 也不会读成明确失败；旧版本写的、可能已生效的失败，本版本一律按结果未知处理。

本版本修不了的旧版本行为（回滚或混跑时的风险）：

- dabb8fd 没有 outcome 概念。回滚到 dabb8fd 后，它的 MQTT 回执和直连维护回执只给 `success=false` 和 stage。平台必须按 stage 判断：`writeback-mismatch`、`writeback-timeout`、`writeback-unconfirmed` 一律按结果未知处理；dabb8fd 自己写的 `writeback-failed` 也可能是超时，同样先核验设备状态，不能当作可重发的明确失败。
- 29f5068 把 `writeback-unconfirmed` 当作最终回执，此后该 cmdId 的真实结果不会再补报。回滚到 29f5068 后，此类命令要按 cmdId 主动查询回执（`pointctl result`、直连维护回执查询）。
- AGC/AVC 与 EMS 策略在所有版本（含本版本）都只看 `success`，任何非成功都会在下一个周期按当前目标重新下发设定值。这是设定值调节的既有行为，设定值写入是幂等的，新标志位不改变这一点。
- 控制账本（`control_dedup.db`）只保存 stage 字符串，不在共享内存验证范围内：旧版本写入账本的 `writeback-failed`，在本版本中按同一 cmdId 重放时仍判为 failed。按第 5 节，旧 cmdId 的结论以升级前的核清记录为准，不依赖升级后的重放。

## 2. 关联服务

以 `deploy/gateway-services.sh` 为准，`/opt/modbus-gateway/bin/gateway-services.sh list-queue` 会列出本机已加载的实例。

写入方（生产者），先停：

| 服务 | 写入入口 |
| --- | --- |
| `mqtt-driver@*` | 平台控制命令；同时承载上位机安全与 OTA 通道 |
| `mqtt-forwarder@*` | 平台转发控制 |
| `system-monitor@*` | 直连维护批量控制接口 |
| `compute-engine@*` | 本机 EMS 策略（图形化/旧版策略） |
| `ems-cluster@*` | EMS 并机调度（为策略提供授权与目标） |
| `agc-avc@*` | AGC/AVC |
| `ky-ems.service`、`qt-display-bridge.service`、`local-display-qt@*` | 本机 KY-EMS 画面控制。`ky-ems.service` 依赖 `qt-display-bridge.service`，停桥接会一并停画面 |

驱动（消费者），后停先启：`modbus-rtu@*`、`dlt645-driver@*`、`dio-driver@*`、`can-driver@*`、`iec-driver@*`。

不动的服务：

- `easytier.service`、`gateway-cellular.service`、`gateway-network-failover.service`，以及系统网络服务。
- `mqtt-tls-tunnel@*`（stunnel，不映射共享内存）。
- `event-engine@*`、`local-display@*`、`local-kiosk@*`（只读画面）、`camera-service@*`、`gateway-disk-guard`。
- `gateway-health-watchdog.service`：不停，由 `stop-writers`/`stop-drivers` 写入的 manual-stop 标记暂停，`start-queue` 成功后恢复。

窗口内不要使用下列命令，它们会作用于全部业务服务或清掉共享内存：

- `gateway-services.sh apply|restart|stop`；
- `systemctl restart gateway-services.service`；
- `gateway-run.sh restart|stop|cleanup`；
- `upgrade-network-resilience.sh`（专用于 4G/网络故障切换的升级，会重启 `gateway-cellular` 与 `gateway-network-failover`）；
- 重启网关。

窗口内也不要用 `pointctl write` 写点。

## 3. 窗口前准备

1. 平台侧确认维护窗口，暂停向本机下发控制。窗口内发来的控制没有回执，平台不得把它们当作已执行。
   - 出厂配置 `mqtt.cleanSession=true`，驱动停止期间的命令不会被补投。
   - 现场如果改成了 `false`，代理会在恢复后补投；其中 `ts` 仍在 `mqttDriver.commandMaxSkewMs`（默认 300000 ms）以内的命令会被执行。这类站点必须由平台在窗口内停发。
2. 按现场规程把受策略控制的设备（PCS、储能等）置于安全状态，并读回确认，例如功率目标 0 或待机。窗口内没有策略监管，设备会保持最后一次设定值。
3. 准备升级包：
   - 本次所有写入方和驱动，以及 `pointctl`，必须在同一个包里同时替换；
   - manifest 的 `restart.services` 留空（由第 4 节第 7 步统一启动），不得包含 `gateway-services.service`，否则会重启全部业务服务；
   - 保留 OTA 备份目录，供回滚使用。
4. 记录当前版本和 `gateway-services.sh list-queue` 的输出，作为启动后的核对清单。

## 4. 升级步骤

以下命令在本机执行（经 EasyTier 维护通道），`APP=/opt/modbus-gateway/config/runtime/apps/mqtt-service.json`。

1. 有 KY-EMS 画面的站点，先在"设备控制"页把控制权限切到"就地"并二次确认，见[EMS平台控制权限](../协议与驱动/EMS平台控制权限.md)。之后平台控制在入口就被拒绝并有回执，已排队的平台命令在执行端也会被拦截。没有画面的站点跳过这一步。
2. 停写入方，驱动继续运行，把队列执行完或判过期：

   ```sh
   /opt/modbus-gateway/bin/gateway-services.sh stop-writers
   ```

3. 至少等待 `memoryStore.pendingWriteMaxAgeMs + 2000` ms（默认 12 s），然后确认队列为空：

   ```sh
   /opt/modbus-gateway/bin/pointctl pending-peek --app-config "$APP"
   ```

   - 必须是 `pending_count=0`。
   - 不为 0 时，说明该点位的驱动没有运行或已卡住，先排查，不要继续。
   - 不要用任何方式手工清空队列：被清掉的命令不会有回执。
   - `pending` 与 `pending-peek` 都只查看、不移除。输出中 `queuedMs` 是排队时长，`queuedMs=unstamped` 表示旧版本入队的命令。
4. 核清在途命令（见第 5 节），全部有结论后再继续。
5. 停驱动：

   ```sh
   /opt/modbus-gateway/bin/gateway-services.sh stop-drivers
   ```

6. 用升级包替换程序（例如本地执行 `ota-apply.sh`，restart 列表为空），并核对替换后的文件哈希。
7. 先启动驱动，再启动写入方；不在清单内的服务不受影响。全部成功后看门狗自动恢复：

   ```sh
   /opt/modbus-gateway/bin/gateway-services.sh start-queue
   ```

8. 核对：
   - `list-queue` 中每个单元 `systemctl is-active` 为 active；
   - `pointctl stats --app-config "$APP"` 正常；
   - `pending-peek` 为空；
   - 点位刷新正常，未连接或过期的点显示 `--`。

   验证阶段不发真实设备写入；如需写入验证，按设备写操作流程另行审批。
9. 第 1 步切过"就地"的站点切回"远程"；平台恢复下发；按现场规程恢复策略和设备运行状态。

## 5. 在途命令核清

在途命令的来源：平台的命令记录、本机策略日志、维护人员记录的 `cmdId`。查询方法：

```sh
/opt/modbus-gateway/bin/pointctl result --cmd <cmdId> --index <index> --shm gateway_point_store
/opt/modbus-gateway/bin/pointctl results --index <index> --limit 20 --shm gateway_point_store   # 该点最近回执，新到旧
```

| 回执 | 结论 | 处理 |
| --- | --- | --- |
| `outcome=succeeded` | 已执行 | 无需处理；有回读要求的点按回读确认 |
| `stage=expired`（`outcome=failed`） | 未执行、已过期 | 唯一允许重新提交的情形：确认业务上仍需要后，用新 `cmdId` 提交（同一 `cmdId` 最多派发一次） |
| `stage=control-rejected` / `rejected` / `rate-limited` / `writeback-skipped` / `malformed-rejected` / `owner-died` | 未执行，被规则拒绝或丢弃 | 不因升级重提；按拒绝原因处理 |
| `stage=writeback-failed`（`outcome=failed`） | 设备明确拒绝 | 不自动重提；按设备原因处理 |
| `outcome=unknown`（`stage=writeback-mismatch` / `writeback-timeout` / `writeback-unconfirmed`，或旧版本写的 `writeback-failed`） | 可能已到设备 | 先核验设备实际状态（回读点 `pointctl get --index <index> --app-config "$APP"`，或在设备侧确认），再人工决定；不得一律重发 |
| 查不到回执，且队列中也没有 | 状态不明 | 按"结果未知"处理（可能在入口就被拒绝，也可能回执已滚出 4096 条环形区） |

## 6. 回滚

触发条件：启动后服务不健康、行为异常，或需要恢复旧版本。

1. 同第 4 节第 1–4 步：暂停入口、`stop-writers`、等待并确认 `pending_count=0`、核清在途命令。
2. `stop-drivers`。
3. 用升级时保留的备份恢复旧程序（例如 `ota-rollback.sh <artifact> <version> <jobId> <backupDir> <stagingDir>`，restart 列表为空），写入方、驱动和 `pointctl` 一起恢复。
4. `start-queue`，然后按第 4 节第 8、9 步核对和恢复。

残留处理：

- 正常流程下切换时队列为空，没有残留。
- 若确有残留（例如某个驱动停止前没执行完）：
  - 回滚后，新版本留下的命令由旧驱动按墙钟规则执行或判过期，均有回执；
  - 升级后，旧版本留下的命令由新驱动一律判过期（`stage=expired`），可按第 5 节在确认后用新 `cmdId` 重提。
- 两种情况都不需要删除共享内存段，也不要执行 `gateway-run.sh cleanup`。
- 回滚后恢复旧语义：墙钟跳变（NTP、手工改时间）会再次影响排队命令的有效期判断。

## 7. 验证工具

在开发机上执行，不连接设备：

```sh
# 当前版本工具：CMake 目标 shm_pending_write_mix
ninja -C build -j1 shm_pending_write_mix
# 旧版本工具：见 tools/shm_pending_write_mix_check.sh 头部（git worktree + 只编 edge_gateway 库 + 编译同一源文件）
sh tools/shm_pending_write_mix_check.sh build/shm_pending_write_mix /tmp/pwmix-dabb8fd /tmp/pwmix-29f5068
# 或注册为 ctest：
cmake -S . -B build -DEDGE_SHM_MIX_OLD_TOOLS="/tmp/pwmix-dabb8fd;/tmp/pwmix-29f5068"
ctest --test-dir build -R shm_pending_write_mix_check
```

相关回归测试：

| 测试 | 覆盖内容 |
| --- | --- |
| `memory_point_store_shm11` | 未打戳的槽永不被信任、单调戳跨进程、旧版本回执的 `writeback-failed` 不读成明确失败 |
| `gateway_services_queue` | 队列动作只停、只启关联服务，从不触及网络、4G、EasyTier 和 TLS 隧道 |
| `pointctl_queue_view` | 查看队列不移除命令 |
| `gateway_daemon_realtime_priority`、`cluster_driver_rejection` | 过期判断 |
| `control_outcome_consistency` | 本版本各回执路径的 outcome 一致 |

迁移回归需要 root，并在独立 PID 命名空间里设置 `GATEWAY_MIGRATION_TEST_BACKUP_DIR` 后运行：

```sh
unshare -fp --mount-proc env GATEWAY_MIGRATION_TEST_BACKUP_DIR=<目录> \
  ctest --test-dir build -R 'memory_point_store_(migration|v11_migration|shm11)'
```
