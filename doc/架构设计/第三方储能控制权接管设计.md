# 第三方储能控制权接管设计

## 1. 目标与设计理由

储能设备平时由边端 EMS 计算并控制 PCS。自有平台或第三方虚拟电厂发来有效功率指令时，需要临时接管指定 PCS 功率点；指令完成、主动退出、租约超时或服务重启后，应自动回归本地 EMS。安全停机、消防、急停等高优先级动作始终可以越过普通控制权。

本设计不关闭本地计算服务，也不让多个控制源同时向 PCS 抢写。所有控制源仍走 PointStore 写队列和原协议驱动，通过同一个持久化所有权文件仲裁。这样既保留现有设备写入、回执和校验链，也能把接管范围限定到明确的 index。

## 2. 控制状态

| 状态 | 普通写入来源 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| 本地 | 本地 EMS、自有平台既有控制链 | 默认状态；服务启动；租约到期；收到 `type=0` | 收到合法且唯一的 `type=1` |
| 第三方接管 | `mqtt-forwarder` | `type=1` 校验、持久化和整组入队成功 | `type=0`、租约到期、转发器停止或重启 |
| 安全覆盖 | 高优先级安全命令 | 任何状态下发生安全动作 | 由原安全控制链结束 |

第三方租约默认 `15000 ms`。每个新的、未处理过的 `type=1` 指令会续租；重复 ID 只返回原结果，不写设备也不续租。本地 EMS 无需停止，接管期间其命中 `ownershipIndexes` 的普通写入会被拒绝，租约结束后自然恢复。

## 3. 消息协议

控制请求只允许平铺 JSON，并拒绝未定义字段。

接管并写入功率：

```json
{"id":"VPP-20260903-0001","type":1,"target":30.0}
```

退出第三方控制：

```json
{"id":"VPP-20260903-0002","type":0}
```

字段说明：

| 字段 | 约束 |
| --- | --- |
| `id` | 必填非空字符串，UTF-8 编码后最多 63 字节；用于幂等和回执关联 |
| `type` | `1` 表示第三方接管并写入，`0` 表示退出并回归本地；也兼容字符串 `"0"`、`"1"` |
| `target` | `type=1` 必填，有限十进制数或十进制数字符串，单位 kW；负数充电、正数放电、零值停功率 |

禁止第三方在报文中伪造 `source`、`highPriority` 或 index。边端拒绝 Broker 在重连订阅时回放的 MQTT RETAIN 历史控制消息，避免旧功率再次执行。MQTT 3 会把在线订阅者首次收到的实时发布清除 RETAIN 标志，边端无法仅凭报文区分发送端是否同时要求 Broker 保留；因此控制 Topic 必须由 Broker ACL 禁止保留发布，发送端也必须固定使用 `retain=false`。十六进制、前导加号、NaN、无穷大和超出配置上下限的目标均拒绝。

回执示例：

```json
{
  "id": "VPP-20260903-0001",
  "type": 1,
  "accepted": true,
  "duplicate": false,
  "mode": "remote",
  "targetKw": 30.0,
  "generation": 12,
  "message": "acquired",
  "ts": 1788400000000
}
```

`accepted=true` 表示控制权和整组共享内存写命令已经接受，不等同于 PCS 已反馈目标功率。设备级执行完成或等待超时后，会在同一 `replyTopic` 追加 `stage=device-result` 或 `stage=writeback-timeout` 的最终结果，原有 JSON 字段保持不变并新增 `success`、各阶段耗时和逐 index 的 `results`。`generation` 是本次所有权代号，执行器会在真实协议写入前再次校验，已退出、已超时或被新指令替代的排队命令不能落到设备。

## 4. 配置

```json
{
  "mqttForward": {
    "enabled": true,
    "protocolVersion": "mqtt3",
    "broker": "ssl://third.example.com:8883",
    "clientId": "",
    "fullTelemetryTopic": "vpp/site/telemetry",
    "fullTelemetryTopicMachineScoped": false,
    "pointIndexes": [501, 502, 503],
    "payloadFormat": "object",
    "qos": 1,
    "intervalMs": 1000,
    "control": {
      "enabled": true,
      "commandTopic": "vpp/site/control",
      "replyTopic": "vpp/site/control/reply",
      "scope": "pcs-power",
      "sessionId": "third-party-vpp",
      "leaseTtlMs": 15000,
      "pollIntervalMs": 100,
      "minTargetKw": -100.0,
      "maxTargetKw": 100.0,
      "ownershipIndexes": [9001, 9002, 9003],
      "targets": [
        {"index": 9001, "scale": 1.0, "offset": 0.0},
        {"index": 9002, "scale": 1.0, "offset": 0.0},
        {"index": 9003, "scale": 1.0, "offset": 0.0}
      ]
    }
  },
  "mqttDriver": {
    "powerControlOwnershipFile": "/opt/modbus-gateway/run/power-control-owner.json"
  }
}
```

- `commandTopic` 和 `replyTopic` 是完整精确 topic，不追加 machineCode。`replyTopic` 可为空，表示不发布业务回执，但不影响本地执行结果链。
- `fullTelemetryTopicMachineScoped=true` 时向 `<fullTelemetryTopic>/<machineCode>` 发布；设为 `false` 时原样使用完整 topic。
- `targets[].index` 必须存在、可写、属于同一个共享内存，并全部包含在 `ownershipIndexes` 中。
- 每个目标实际写值为 `target * scale + offset`。三相同功率可配置三个目标；设备需要总功率换算时应按协议明确设置比例，不能靠运行时猜测。
- `ownershipIndexes` 可比 `targets` 更宽，用于接管期间一并阻止会与第三方目标冲突的本地辅助功率点。
- `ownershipFile` 通常省略并继承 `mqttDriver.powerControlOwnershipFile`；显式填写时必须与主 MQTT 完全一致。启用 AGC/AVC 时其 `ownership.leaseFile` 也必须一致。
- 控制最终结果数据库不新增必填配置。默认路径由 `ownershipFile` 派生：`.json` 后缀替换为 `.control-results.db`，其他路径追加 `.control-results.db`。
- 控制启用时 `mqttForward.qos` 必须是 `1` 或 `2`。最终结果使用可靠发布，只有收到对应 MQTT ACK 后才标记为已交付。
- `leaseTtlMs` 允许 `1000..60000`，`pollIntervalMs` 允许 `10..1000`。生产默认推荐 `15000` 和 `100`。

## 5. 执行链与优先级

```text
第三方精确 topic
  -> 严格 JSON/范围/RETAIN/重复 ID 校验
  -> 持久化待处理回执并获取 generation 租约
  -> PointStoreRouter 整组原子入队
  -> Modbus/DLT645/CAN 执行器再次校验 owner + index + generation + 有效期
  -> 设备写入及既有写回结果
```

普通优先级从高到低为：当前合法接管者、无接管时的本地控制。高优先级安全命令不受普通租约阻挡，也不要求第三方 generation。第三方请求不能把自己标为高优先级。

来源为 `mqtt-forwarder` 的普通命令必须同时满足：租约仍有效、index 位于当前接管范围、generation 与当前租约一致。即使命令把 generation 伪装成 `0`，在无租约、租约到期或主动退出后也不能进入现场协议写入；本地 EMS 的 generation `0` 兼容路径不受影响。

所有权状态使用临时文件、落盘同步和原子替换写入。文件损坏、锁失败或 generation 不匹配时普通写入按失败关闭处理；不能因为状态文件异常而放行多个普通控制源。

状态文件损坏不会靠服务重启自动放行。现场恢复时应先停止控制生产者和协议驱动，备份并移除损坏的所有权文件及其 `.lock` 文件，再按同一批次启动全部进程；禁止在仍有写入进程运行时直接删除。

## 6. 幂等、结果恢复与时钟

- `type=1` 在设备写入入队前先建立持久化 `pending`。重启后恢复 pending 并继续等待既有写回结果，不重新写设备。
- 设备完成或超时后，最终 MQTT payload 先原样写入 SQLite，再调用 `publishReliableJsonMessage()`；协议 ACK 成功后才标记 `delivered`。进程重启、Broker 拒绝或断链都会保留未交付结果，后续重放同一字节 payload。
- 同一 `type=1` ID 的幂等判断优先查询控制结果数据库，不受所有权文件只保留最近 64 条 receipt 的淘汰影响。pending 重试不写设备，final 重试重放已保存 payload；变更 type、target 或映射后复用同 ID 会被拒绝。
- 所有权文件中的 64 条 receipt 继续服务于非设备结果类的短窗口兼容判断。第三方仍必须使用全局唯一、不可循环复用的 ID。
- 转发器启动时清理自身任意旧 session 的租约并推进 generation，因此修改 `sessionId` 后重启也立即回归本地；不会清理其他 owner 的有效租约。
- 正常停止仅释放当前 session，避免两个误并行实例互相清理。
- 租约使用边端墙上时钟毫秒值。上线前必须确保系统时钟稳定；时间大幅回拨会延长租约，时间大幅前跳会提前回归本地。

事件 Outbox 与控制轮询仍在同一 Forwarder 线程中。控制启用时，每次 `runOnce()` 最多可靠补发一条事件，下一轮先轮询控制；这只限制批量积压造成的连续等待。当前单次 `publishReliableJsonMessage()` 没有覆盖连接、发送和 ACK 全过程的绝对 deadline，因此一次发布本身仍可能无界阻塞，不能把该调度规则描述为硬实时保证。

## 7. 兼容与发布

- 缺少 `mqttForward` 或 `mqttForward.enabled=false`：不启动转发器，旧设备行为不变。
- `mqttForward.enabled=true` 且 `control` 缺失/关闭：保持原 TX-only，上行兼容不变，不建立 RX 连接，不发送 SUBSCRIBE。
- `control.enabled=true`：仅增加一个第三方控制订阅，不开放主 MQTT 的 OTA、配置、诊断、实时监测等 topic。
- 本变更把共享内存布局升级到版本 9。生产更新时必须同时替换写队列生产者和 Modbus/DLT645/CAN 消费者，并在停服务后清理旧共享内存段，再统一启动。
- 通用出厂包和老旧项目上行迁移默认不得开启第三方控制。先验收两路上行，再单独灰度控制。

## 8. 灰度验收与回滚

1. 备份 app 配置、全部相关驱动和共享内存版本产物。
2. 在测试设备停统一服务，替换同一构建批次的转发器、共享内存库和协议驱动，清理旧共享内存，再启动。
3. 保持 `control.enabled=false`，确认自有平台和第三方上行与升级前一致。
4. 启用控制后先发送 `target=0`，确认回执、所有权文件、设备写回结果和本地 EMS 暂时被阻挡。
5. 用允许范围内的小功率分别验证充电、放电、重复 ID、不续租、`type=0`、15 秒超时和服务重启回归本地。
6. 在第三方接管期间触发测试用高优先级安全命令，确认其可以执行；随后确认过期第三方排队命令不会再次写设备。
7. 在转发器离线时写入一条测试 RETAIN 命令，再启动转发器，确认其被拒绝且控制权仍为本地；同时检查 Broker ACL 已禁止控制 Topic 的保留发布。
8. 任一项失败，先设置 `control.enabled=false` 并重启转发器；仍异常则恢复整批二进制和配置，清理共享内存后统一启动。

生产替换前必须完成 Windows 单元测试、Linux 原生测试、全志 AArch64 交叉编译和一台非生产设备实机冒烟。不能只替换 `MqttForwarder` 单个二进制。
