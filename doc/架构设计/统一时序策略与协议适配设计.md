# 统一时序策略与协议适配设计

## 1. 目标

边端过去分别配置采集周期、点位周期、串口帧间隔、共享内存处理循环和 MQTT 上送周期。同一个业务目标需要重复填写多个毫秒值，而且不同协议使用的字段不同，容易出现以下问题：

- 修改 `transport.pollIntervalMs` 后界面显示已保存，但边端实际只读取 `collect.defaultIntervalMs`。
- 串口没有配置 `frameIntervalMs` 时，错误回退到 `collect.defaultIntervalMs`，导致 5 秒采集周期同时变成 5 秒帧间隔。
- Win 端允许填写 1ms，边端运行时却静默钳制到 100ms，操作员无法判断真实生效值。
- `mqttDriver.scanIntervalMs` 同时影响 MQTT 下行、实时会话和补传调度，“共享内存扫描间隔”的名称不准确。
- CAN 的 `receiveTimeoutMs`、`interfaceCheckIntervalMs` 已能解析，但旧运行时没有真正执行。

本设计使用“统一语义策略 + 协议能力适配器 + 分层覆盖 + 专家参数”，让操作员先表达业务目标，再由边端翻译成协议参数。

## 2. 核心原则

1. 统一的是业务语义，不是强迫所有协议使用同一个数值。
2. 语义档位必须可解释，Win 端显示参数来源和预计生效值。
3. 设备、点位可以覆盖项目默认；留空表示继承。
4. 协议专用参数继续保留，不塞入通用字段。
5. 低于协议能力下限时直接拒绝配置，不再静默钳制。
6. 没有 `timingPolicy` 的旧工程按 `custom` 兼容，不自动改变已有周期。

## 3. 配置层级

```text
项目默认（runtime/apps/*.json）
  -> 设备/链路（runtime/devices/*.json）
    -> 点位组（后续可选）
      -> 单点 read.intervalMs / cachePolicy.ttlMs
```

优先级从低到高。当前实现已支持项目、设备和单点三级；点位组继续沿用组内单点配置，不额外制造一套重复字段。

## 4. 响应等级

| 档位 | 目标新鲜度 | 最大有效期 | 请求间隔 | 响应超时 | 重试 | MQTT 合并窗口 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `ultraFast` 极低延迟 | 50ms | 500ms | 2ms | 100ms | 1 | 10ms |
| `highFrequency` 高频 | 200ms | 2s | 5ms | 300ms | 1 | 20ms |
| `realtime` 实时 | 500ms | 5s | 10ms | 800ms | 1 | 50ms |
| `standard` 标准 | 1s | 10s | 20ms | 1s | 2 | 100ms |
| `normal` 普通 | 5s | 30s | 50ms | 2s | 2 | 500ms |
| `slow` 慢速 | 60s | 180s | 100ms | 3s | 1 | 1s |
| `inherit` | 继承项目默认 | 继承 | 继承 | 继承 | 继承 | 继承 |
| `custom` | 使用旧字段或高级覆盖 | 自定义 | 自定义 | 自定义 | 自定义 | 自定义 |

档位是默认策略，不是硬编码。高级覆盖只写需要偏离档位的参数。

### 上送模式

| 模式 | 普通变位事件 | 告警事件 | 全量校准 |
| --- | --- | --- | --- |
| `onChange` | 开启 | 开启 | 按 `heartbeatMs` 执行 |
| `periodic` | 关闭 | 开启 | 按 `heartbeatMs` 执行 |
| `hybrid` | 开启 | 开启 | 按 `heartbeatMs` 执行 |

`periodic` 只关闭 `reportOnChange` 普通变位，不能关闭告警。`onChange` 与 `hybrid` 都保留变位事件；二者配置了 `heartbeatMs` 时都会发送低频全量校准，避免长期无变化导致平台无法确认当前全量状态。

`batchWindowMs` 是期望的变化合并窗口，`maxLatencyMs` 是硬性最长延迟。有效 EventEngine 扫描周期和 MQTT 事件补发周期取两者较小值；只配置 `maxLatencyMs` 时，它也会限制旧的 `scanIntervalMs`。当前运行时最低调度粒度为 10ms。

## 5. JSON 结构

```json
{
  "timingPolicy": {
    "profile": "ultraFast",
    "acquisition": {
      "targetFreshnessMs": 50,
      "maxAgeMs": 500
    },
    "delivery": {
      "mode": "onChange",
      "maxLatencyMs": 50,
      "batchWindowMs": 10,
      "heartbeatMs": 60000
    },
    "overrides": {
      "pollIntervalMs": 40,
      "requestGapMs": 2,
      "responseTimeoutMs": 100,
      "retryCount": 1,
      "interfaceCheckIntervalMs": 100,
      "receiveWaitMs": 10,
      "mqttScanIntervalMs": 10
    }
  }
}
```

项目配置可填写完整结构。设备配置通常只填写 `profile` 和少量 `overrides`。

## 6. 协议适配矩阵

| 协议 | `targetFreshnessMs` | `requestGapMs` | `responseTimeoutMs` | `retryCount` | 专家参数 |
| --- | --- | --- | --- | --- | --- |
| Modbus RTU | 轮询和未显式点位周期 | 同从站请求帧间隔 | 串口响应超时 | 单帧立即重发 | 批量寄存器、轮次退避、拆包探测 |
| Modbus TCP | 轮询和未显式点位周期 | 不作为 TCP 强制延迟 | TCP 响应超时 | 当前不额外重发 TCP 事务 | 连接超时、最大寄存器数 |
| DLT645 | 轮询和未显式点位周期 | 同表地址请求帧间隔 | 串口响应超时 | 读命令立即重发 | 唤醒字节、写密码 |
| IEC101/103 串口 | 轮询窗口 | 串口帧间隔 | 轮询响应超时 | 主动轮询重发 | 链路地址、总召参数 |
| IEC103/104 TCP | 轮询/总召目标 | 不强制使用 | TCP 响应超时 | 主动轮询重发 | `t0/t1/t2/t3`、K/W 窗口 |
| CAN | 事件接收循环 | 不适用 | 不适用 | 不适用 | 波特率、sample point、帧级 `receiveTimeoutMs` |
| 本机 DIDO | GPIO 扫描周期 | 不适用 | 不适用 | 不适用 | 单点防抖、取反 |
| ComputeEngine | 计算调度周期 | 不适用 | 不适用 | 不适用 | 规则触发器和单规则最小周期 |
| MQTT | 不直接采集 | 不适用 | 下行命令另行控制 | 不适用 | 合并窗口、全量校准、离线补传 |

CAN、IEC104 的自发上送是事件模型，不套用 Modbus 的轮询退避。

## 7. 协议最低可达周期

| 类型 | 最低配置值 |
| --- | ---: |
| 本机 DIDO | 1ms |
| CAN | 5ms |
| 虚拟点/计算点 | 10ms |
| Modbus、DLT645、IEC 主动轮询 | 20ms |

最低值只表示调度器允许执行，不保证链路能在该时间内完成所有请求。实际端到端周期还受以下因素影响：

```text
设备数量 x 每设备请求帧数 x（报文线速时间 + 响应时间 + 帧间隔 + 重试）
+ 共享内存处理
+ MQTT 合并与网络时延
```

因此 Win 端显示“协议最低值”和“预计生效值”，现场仍需用报文时间戳验收。

## 8. 失败重试与轮次退避

- 立即重试用于处理偶发丢帧，次数来自 `retryCount`。
- 连续失败达到 `slaveFailureBackoffThreshold` 后，按 `1 -> 2 -> 4...` 个采集轮次跳过。
- 跳过上限来自 `taskFailureBackoffMaxCycles`。
- 一次成功立即清空连续失败和剩余跳过轮次。
- Modbus 继续保留任务级拆分和单任务退避。
- DLT645、IEC101/103 主动轮询使用通用轮次退避。
- CAN 和 IEC 自发事件接收不做轮次退避；CAN 使用静默超时和接口恢复。

## 9. CAN 失效和接口恢复

- 每个 CAN 点的 `read.can.receiveTimeoutMs` 单独计时。
- 点位至少成功接收一次后，超过静默时间会保留最后值，但写入 `quality=0` 和 `stale=true`。
- 下一帧成功解析后恢复 `quality=1`。
- `collect.interfaceCheckIntervalMs` 周期检查 SocketCAN 接口 `IFF_UP`。
- 接口掉线时关闭旧 Socket，按 `manageInterface` 配置恢复接口并重新绑定。

## 10. 旧字段迁移

| 旧字段 | 当前读取 | 保存迁移 |
| --- | --- | --- |
| `transport.pollIntervalMs` | 仅 Win 兼容读取 | 写为 `collect.defaultIntervalMs` |
| `protocol.transport.pollIntervalMs` | 仅 Win 兼容读取 | 删除别名 |
| `transport.maxBatchSize` | 仅 Win 兼容读取 | 写为 `collect.maxBatchRegisters/maxRequestRegisters` |
| 未配置 `frameIntervalMs` | 不再回退到采集周期 | 使用独立默认 0ms 或档位值 |
| `mqttDriver.scanIntervalMs` | 继续兼容 | 推荐由 `timingPolicy.delivery.batchWindowMs` 计算 |

## 11. 运行时实现

- 配置模型：`include/edge_gateway/models.hpp`
- 解析：`src/config_loader.cpp`
- 语义解析与协议适配：`src/timing_policy.cpp`
- 采集循环：`src/common/gateway_daemon.cpp`
- 点位周期：`src/common/collector_base.cpp`
- CAN 静默失效/接口恢复：`src/can_driver_service.cpp`
- MQTT 调度：`src/mqtt_driver_service.cpp`
- 通用写回调度与耗时：`src/writeback_service.cpp`

采集守护循环使用所有已启用可读点中的最短实际周期。设备级
`collect.defaultIntervalMs` 只作为未配置点位周期时的回退值，不能在所有点位均有
显式周期时额外制造更快的空循环。例如设备默认 2ms、全部点位均为 100ms 时，
守护循环按 100ms 运行；存在真实 2ms 点位时仍按 2ms 运行。

共享内存 owner/claim 心跳和过期槽物理清理不再随每次采集或每帧 CAN 报文执行，
统一按 5 秒维护。点值读取仍根据 `expireAt` 即时计算 `stale`，因此物理清理降频
不会延迟质量失效判断。

## 12. 通用写回契约

Modbus、DLT645、IEC、DIDO 和 CAN 使用相同的共享内存命令队列、优先级租约和结果字段：

- 活跃高优先级租约存在时，只取该 `cmdId` 且标记为高优先级的命令，普通命令保留在队列中。
- `requestedAt` 是请求时间，`acceptedAt` 是边端接受时间，`startedAt`/`completedAt` 是真实设备写入起止时间。
- `queueDelayMs = startedAt - acceptedAt`，`deviceWriteMs = completedAt - startedAt`。
- `edgeElapsedMs = completedAt - acceptedAt`，`totalElapsedMs` 至少等于排队与设备写入耗时之和。
- `stage` 统一为 `writeback-succeeded`、`writeback-failed`、`writeback-skipped` 或 MQTT 侧的 `writeback-timeout`。
- `highPriority`、回读校验结果和各阶段耗时必须跨共享内存完整返回。

## 13. 验收标准

1. Win 修改采集周期后，JSON 必须出现 `collect.defaultIntervalMs`。
2. 5 秒采集周期且未填写帧间隔时，连续串口请求之间不得固定等待 5 秒。
3. 低于协议最低周期时，dryRun 必须返回明确错误。
4. 单点显式 `read.intervalMs` 不被项目或设备档位覆盖。
5. CAN 点超过 `receiveTimeoutMs` 后质量变为 0，恢复报文后质量回到 1。
6. DLT645、IEC 主动轮询连续失败后按轮次退避，恢复后一次成功立即重新上线。
7. MQTT 极低延迟档位下处理循环不再被固定 100ms 下限阻挡。
8. `periodic` 模式不发送普通变位事件，但告警必须正常发送。
9. 高优先级写入结果跨进程读取后仍保留 `highPriority=true`，CAN 与其他采集驱动返回相同阶段和耗时字段。

## 14. 22.16 真机验证记录（2026-08-03）

测试设备：`192.168.22.16 / COMM202600999`。

- 11 个 AArch64 原生调度和协议测试全部通过。
- 真实 Modbus TCP 的 7 个从站、77 个点均保持 `quality=1`。
- 隔离影子配置同时运行健康从站和不存在的从站；健康点持续更新，失败点进入
  `quality=0`，45 秒内执行 20 次失败探测，没有阻塞健康从站。
- MQTT TLS 到 `kygate.kyxn.net:8883` 的两条连接在观察期内保持稳定。
- 高优先级 DIDO 同值写回被正常消费并完成回读，没有改变现场输出状态。
- 六轮稳定性采样中，采集、计算、事件和 MQTT 服务均为 `NRestarts=0`，无
  warning 级日志，写队列无积压。
- DIDO CPU 从错误空转时的 76% 降至约 14.8%；剩余占用来自 7 个实际配置为
  2ms 的 DI 点。CAN CPU 从约 11.3% 降至约 0.5%。
