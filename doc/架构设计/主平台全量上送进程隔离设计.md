# 主平台全量上送进程隔离设计

## 1. 目标与原因

周期 full 的分片编码、网络发送和 QoS 应答原来都在 `MqttDriver` 扫描线程中执行。大点表或弱网络会拖慢控制、OTA、实时监控和回执处理。改造目标是把周期 full 放入独立数据面工作器，同时保留主驱动兜底，不能因为拆进程扩大断链时间。

## 2. 职责边界

```text
协议驱动 / ComputeEngine
          -> PointStoreRouter
               -> MqttDriver
                  控制、OTA、实时监控、状态、告警与事件补发
                  主 full 故障兜底
               -> MqttForwarder: primary-full worker
                  自有平台周期 full、最新快照、快速重连
               -> MqttForwarder: mqttForward worker
                  第三方上送、可选第三方控制
```

一个 `MqttForwarder` 进程可以同时托管主平台 full 和现有第三方输出。每个输出有独立 MQTT ClientId、周期、重试状态和健康文件；一个输出失败不得阻塞另一个输出。

## 3. 发布权状态机

| 状态 | 发布者 | 行为 |
| --- | --- | --- |
| 启动等待 | 主驱动暂缓 | 给工作器一个有界启动窗口，避免双方首包重复 |
| `claiming` | Forwarder | 首次或恢复发送当前 full；短租约只覆盖本次发送 |
| `active` | Forwarder | 已收到 QoS 应答或 MQTT 探活应答，按周期发送并续租 |
| `retrying` | 主驱动 | Forwarder 释放租约，按 0.5/1/2/4/5 秒重试 |
| 租约过期 | 主驱动 | 下一扫描周期立即补发当前 full，不等待 30 秒业务周期 |

默认参数为 `1s` 探活、`3s` 租约、`500ms` 最小重试、`5s` 最大重试。业务 `fullUploadIntervalMs` 不参与断链检测和恢复等待。

健康文件写入临时文件后原子替换。Forwarder 在声明发布权和发送 full
前，必须先持有跨进程文件锁；Driver 兜底发送也使用同一把锁。锁文件放在
`/opt/modbus-gateway/run`，不能放在 Forwarder 的 systemd `RuntimeDirectory`
中，否则停止 Forwarder 时 systemd 会删除锁目录，导致 Driver 无法接管。

有效发布权必须同时满足：

- `primaryFullUpload=true`；
- 状态是 `claiming`，或状态是 `active` 且 `healthy=true`；
- `heartbeatAtMs` 未超过故障切换窗口；
- `leaseUntilMs` 尚未到期。
- `machineCode`、`clientId` 和 `topic` 与当前配置完全一致。

文件缺失、损坏、超时或 `retrying` 均按无租约处理，主驱动 fail-open 兜底。

## 4. 数据一致性

- 主驱动与 Forwarder 复用 `resolveFullUploadIndexes()`，不维护两份点集。
- 主工作器继承主 MQTT 的 full topic、machineCode 作用域、载荷格式和 `maxPayloadBytes`，平台分片解析不变。
- full 只表达最新状态，发送失败不落历史队列；恢复时重新读取共享内存。
- 告警、变化事件和控制回执表达历史事实，继续使用可靠 outbox，不随 full 改造。
- 主工作器沿用主驱动的 PointStore 容错语义；第三方输出保留原来的严格点集隔离。
- PointStore v9 与现场 v8 保持二进制布局兼容。程序可以直接打开 v8 段且不会
  改写其版本；新建段使用 v9，避免仅升级 MQTT 进程时迫使采集服务一起重启。

## 5. 兼容与启用

没有 `fullUploadWorker` 或 `mode=inline` 时完全按旧模式运行。启用顺序：

1. 同批次部署 `MqttDriver`、`MqttForwarder`、`gateway-services.sh` 和 systemd unit，配置仍保持 `inline`。
2. 确认旧 full、控制、OTA、实时监控和事件正常。
3. 把 `mode` 改为 `isolated`，只重启 `mqtt-driver@mqtt-service` 和 `mqtt-forwarder@mqtt-service`，不要执行全局 apply。
4. 检查主 ClientId 为 machineCode，full ClientId 为 `<machineCode>-full`，两者不得相同。
5. Broker 实收一套完整 full 后，再进行故障注入。

回滚时先停止 Forwarder，等待主驱动兜底 full 到达，再把 `mode` 改回 `inline` 并重启主驱动。

## 6. 验收矩阵

| 场景 | 通过标准 |
| --- | --- |
| 正常运行 | 每个业务周期只有一套完整主 full；控制、OTA、实时和事件正常 |
| Forwarder 首次启动失败 | 约 3 秒后主驱动发送当前 full |
| `kill -9 MqttForwarder` | `failoverTimeoutMs + scanIntervalMs` 内主驱动接管 |
| Broker 断开 | 健康状态转 `retrying`，不等待业务周期，按快速退避重连 |
| Broker 恢复 | 立即发送最新快照，不回放断链期间历史 full |
| 单 PointStore 异常 | 主 full 继续包含其他可用存储区的数据 |
| 第三方 Broker 异常 | 主平台 full、控制和实时链路不受影响 |
| 整机重启 | 启动等待有界，无长期双发；工作器正常后重新取得租约 |

当前实现以单个主 full 工作器为边界。健康租约负责故障判定，持久文件锁负责
跨进程互斥，两者缺一不可。系统时间大幅回拨和平台端分片事务提交属于后续增强项，
不应通过同时启动多个同配置 Forwarder 来规避。

## 7. 现场故障注入注意事项

- 停止 Forwarder 后，Driver 应在 `failoverTimeoutMs + scanIntervalMs` 内接管；
  兜底发送失败后按 `retryMinMs` 起步退避，不再重新等待启动宽限期。
- `publishFullOnStart=false` 同时约束 Forwarder 和 Driver 兜底，不能由兜底路径绕过。
- Forwarder 无法原子写入 `claiming` 健康状态时不得发送 full，避免“已经发送但
  Driver 看不到租约”造成双发。
- DNS、TCP 和 TLS 建连必须在取得跨进程发布锁之前完成。弱网下名称解析可能阻塞
  十秒以上；若建连期间持锁，即使健康租约已经失效，Driver 也无法在规定时间内接管。
  连接探活失败时 Forwarder 写入 `retrying` 并释放发布权，Driver 继续发送 full。
- 恢复 Forwarder 时先看到身份匹配的 `active` 健康文件，再确认 Driver 停止兜底；
  不能只以 systemd 的 `active` 状态判断发布权已经切换。
