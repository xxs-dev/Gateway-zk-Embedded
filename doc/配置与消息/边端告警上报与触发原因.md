# 边端告警上报与触发原因

本文根据当前边端源码和仓库配置整理，回答以下问题：

- 哪些事件会通过 MQTT 作为告警上报平台。
- 每种告警的触发条件、恢复条件、重复策略和数据来源。
- 当前 EMS 工程中有哪些设备故障点和本地 SCADA 告警。
- 哪些异常只是状态、回执或日志，并不属于平台告警。

审计基线：2026-08-13，分支 `integration/edge-runtime-stabilization-20260807`。

> 设备经过 Win 工具或平台写回配置后，实际运行配置可能与仓库基线不同。现场最终清单必须以设备上 `mqtt-service.json` 的 `deviceConfigFiles[]` 及这些文件中的 `points[].alarms[]` 为准。

## 1. 结论总览

边端当前只有两条真正的 MQTT 告警发布路径。

| 类型 | 是否上报平台告警 | 实际 Topic | 触发来源 |
| --- | --- | --- | --- |
| 通用测点告警 | 是 | `edge/alarm/<machineCode>` | 已加载设备配置中点位的 `alarms[]` |
| 系统监测告警 | 是 | `edge/system/monitor/alert/<machineCode>` | CPU、内存、磁盘和 4G 状态 |
| EMS 2.0 SCADA 告警 | 否，仅本机画面 | 无 | `.kyscada` 工程的 `alarms.json` |
| EMS 1.0 SCADA 告警 | 当前无规则 | 无 | 当前 `alarms.json` 为空 |
| 设备通信失败、点位离线 | 默认不是告警 | 实时数据或变位 Topic | `quality/stale/device_online` |
| 控制、OTA、配置、录波失败 | 不是告警 | 各自的 reply/status Topic | 操作结果和任务状态 |
| 服务异常和驱动错误 | 不是告警 | `edge/status` 或本地日志 | 服务状态事件、systemd、journal |

当前仓库基线还应特别注意：

1. 默认 `mqtt-service.json` 已启用 `eventEngine`，但它实际加载的默认设备文件中没有非空 `alarms[]`，因此默认包不会产生设备测点告警。
2. 仓库中只有 `device_alarm_multi_slave_tcp_1_2.json` 带两个阈值告警示例，但该文件没有被默认 `deviceConfigFiles[]` 引用。
3. EMS 2.0 有 37 条本地 SCADA 告警规则，但这些规则目前不会自动转换成 `edge/alarm` 消息。
4. 系统监测有 6 个告警指标，默认随 `monitor-service` 启用，不依赖用户打开实时监测页面。

## 2. 通用测点告警

### 2.1 生效条件

一个点位要上报测点告警，必须同时满足：

1. 设备 JSON 被当前 `mqtt-service.json` 的 `deviceConfigFiles[]` 引用。
2. `eventEngine.enabled=true`。
3. 点位存在非空 `alarms[]`。
4. 该点位已路由到 EventEngine 能访问的共享内存。
5. `mqtt.alarmTopic` 非空，且 MQTT 发布链路可用或事件已进入 outbox。

任何使用统一 `PointDefinition` 的协议都可以配置测点告警，包括 Modbus、DL/T 645、DIDO、CAN、IEC101/103/104、EMS 虚拟点和 AGC/AVC 虚拟点。协议驱动本身不会因为点名含“故障”就自动生成告警。

### 2.2 支持的规则

当前只支持 `high` 和 `low` 两类规则。

| 类型 | 激活条件 | 恢复条件 |
| --- | --- | --- |
| `high` | `value >= threshold` | `value < threshold` |
| `low` | `value <= threshold` | `value > threshold` |

行为规则：

- 第一次收到的值已经满足条件时，立即发布 `active=true`。
- 告警持续期间不重复发布测点告警。
- 离开条件且 `reportRecovery=true` 时，发布一次 `active=false`。
- `reportRecovery=false` 时只发激活，不发恢复。
- EventEngine 重启后内存状态清空；重启后的第一个异常值会再次发布激活。
- 当前没有延时、滞回、连续次数、严重等级、确认状态、`eq/ne` 或位掩码规则。

配置示例：

```json
{
  "index": 11001,
  "pointCode": "temperature",
  "name": "柜内温度",
  "alarms": [
    {
      "type": "high",
      "threshold": 50,
      "reportRecovery": true,
      "persistValue": "temperature-high"
    }
  ]
}
```

二值点和在线状态常用写法：

```json
{
  "name": "消防动作",
  "alarms": [
    { "type": "high", "threshold": 0.5, "reportRecovery": true }
  ]
}
```

```json
{
  "name": "设备在线状态",
  "read": { "dataType": "device_online" },
  "alarms": [
    { "type": "low", "threshold": 0, "reportRecovery": true }
  ]
}
```

非负整数故障字需要“任意非零即告警”时，可以使用 `high + threshold=1`。如果需要判断特定位，当前平台告警引擎不能直接使用 `bitSet/maskAny`，应先派生独立二值点，再给派生点配置告警。

### 2.3 MQTT 消息

实际 Topic：

```text
edge/alarm/<machineCode>
```

激活示例：

```json
{
  "type": "alarm",
  "machineCode": "COMM202600104",
  "meterCode": "PCS_001",
  "index": 1212,
  "pointCode": "total_fault",
  "alarmType": "high",
  "active": true,
  "value": 1,
  "quality": 1,
  "ts": 1786579200000,
  "stale": false
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `alarmType` | 当前为 `high` 或 `low`，不是业务告警名称 |
| `active` | `true` 为发生，`false` 为恢复 |
| `quality` | 点位质量，正常通常为 `1` |
| `stale` | 点位是否过期 |
| `ts` | 触发判断所使用点值的时间戳 |

当前 `AlarmEvent` 内部保存了 `threshold`，但 MQTT JSON 没有输出该字段；严重等级、点位中文名、告警描述也不在消息中。平台需要通过 `machineCode + meterCode + index/pointCode` 查询点表补齐业务名称。

### 2.4 质量、持久化和断线补传

- 当前测点告警判断没有排除 `quality=0` 或 `stale=true`。异常质量点仍会按数值比较，平台必须同时查看 `quality/stale`，这是当前实现限制。
- `persistValue` 非空时，激活和恢复事件写入 `alarmStore.sqlitePath`，默认是 `/opt/modbus-gateway/data/alarm_events.db`。
- `persistValue` 为空时，即使 `alarmStore.enabled=true`，该事件也不会写本地告警表，但仍可通过 MQTT 上报。
- 默认 EventEngine 使用 `publishMode=mqtt_driver_outbox`，事件写入 MQTT SQLite outbox；MQTT 恢复后优先重放告警，再重放变位。
- outbox 超过磁盘上限需要淘汰数据时，先淘汰非告警事件，告警最后淘汰。

### 2.5 当前仓库中的测点规则

当前扫描到的非空 `points[].alarms[]` 只有两条：

| 文件 | 点位 | 条件 | 恢复 | 本地告警库 |
| --- | --- | --- | --- | --- |
| `config/runtime/devices/device_alarm_multi_slave_tcp_1_2.json` | `TCP_SLAVE0001 / index=21001 / reg_1` | 值 `>=1000` | 是 | 否，`persistValue` 为空 |
| 同上 | `TCP_SLAVE0002 / index=22001 / reg_1` | 值 `>=1000` | 是 | 否，`persistValue` 为空 |

该文件是测试示例，没有被当前默认 `mqtt-service.json` 引用。默认运行配置和出厂配置实际加载的串口、DIDO、EMS 虚拟点文件，其 `alarms[]` 当前均为空。

`mqttDriver.alarmRules` 虽然仍有配置模型和解析代码，但当前没有运行时消费逻辑，不能作为有效告警配置入口。应统一使用点位 `alarms[]`。

## 3. 系统监测告警

### 3.1 Topic 和消息格式

实际 Topic：

```text
edge/system/monitor/alert/<machineCode>
```

消息格式：

```json
{
  "type": "system-alert",
  "machineCode": "COMM202600104",
  "metric": "cpuUsage",
  "level": "critical",
  "value": 95.2,
  "threshold": 90,
  "active": true,
  "message": "cpu usage too high",
  "ts": 1786579200000
}
```

当前所有系统告警的 `level` 固定为 `critical`，不能按指标单独配置等级。

### 3.2 完整指标清单

仓库默认监测周期为 5 秒，重复上报间隔为 60 秒。

| `metric` | 中文含义 | 默认触发条件 | 恢复条件 | 原因和英文 `message` |
| --- | --- | --- | --- | --- |
| `cpuUsage` | CPU 使用率过高 | 连续 3 个样本 `>=90%` | 连续 3 个样本 `<=80%`，发布 `active=false` | CPU 持续繁忙；`cpu usage too high` / `cpu usage recovered` |
| `memUsage` | 内存使用率过高 | 单个样本 `>=90%` | 当前未实现恢复消息 | `MemAvailable` 过低；`memory usage too high` |
| `diskUsage` | 根分区使用率过高 | 单个样本 `>=90%` | 当前未实现恢复消息 | `/` 可用块不足；`disk usage too high` |
| `cellularPresent` | 未发现 4G 模组 | `cellular.enabled=true` 且未找到模组 | 当前未实现恢复消息 | USB/串口/ModemManager 未发现模组；`cellular modem not found` |
| `cellularConnected` | 4G 网络未连接 | 已发现模组，但 `connected=false` | 当前未实现恢复消息 | 模组存在但没有可用蜂窝连接；`cellular network not connected` |
| `cellularSignalPercent` | 4G 信号过弱 | 信号有效且 `<20%` | 当前未实现恢复消息 | 无线信号低于阈值；`cellular signal too weak` |

补充说明：

- CPU 使用率来自相邻两次 `/proc/stat` 差值；服务启动后的第一次采样用于建立基线。
- CPU 在启动后连续 3 个健康样本会主动发布一次 `active=false`，用于清除平台可能残留的旧 CPU 告警。
- 内存使用率计算为 `(MemTotal-MemAvailable)/MemTotal`。
- 磁盘使用率来自根分区 `/` 的 `statvfs`。
- `load1` 和 `processCount` 会出现在系统遥测中，但当前没有对应告警。
- `registered=false`、`simReady=false`、路由没有切到 4G、流量为 0 当前都没有独立告警指标。
- 模组缺失时只发 `cellularPresent`，不会同时发 `cellularConnected`。
- 告警判断按 `defaultIntervalMs` 周期执行，不依赖监测页面订阅租约。

### 3.3 重复、恢复和断线行为

- 状态第一次出现时立即发布。
- 状态不变时按 `alertRepeatIntervalSec` 重复发布，默认 60 秒。
- CPU 是当前唯一完整实现恢复上报的系统指标。
- 内存、磁盘和 4G 指标恢复后不会发 `active=false`。平台不能仅凭长时间没收到重复消息判定恢复，应结合系统遥测或后续修复恢复逻辑。
- 当前 `monitor-service.json` 的 `mqtt.offlineBuffer.enabled=false`。系统监测告警使用普通 MQTT 发布，默认没有磁盘级断线补传；发送失败时可能丢失本次告警。
- 默认普通 MQTT QoS 为 1，但 QoS 不能替代边端断线期间的本地持久化。

### 4.6 SCADA 告警的当前边界

- `severity` 和当前条件会用于本机告警列表显示。
- `requiresAcknowledgement` 当前主要是工程元数据，不会生成 MQTT 确认流程。
- `delayMs/deadband` 已能被工程加载器读取和校验，但当前 Qt 活动告警渲染路径只按实时比较结果显示；本工程的这两个值也全部为 0。
- SCADA 告警不写 `/opt/modbus-gateway/data/alarm_events.db`，不走 MQTT outbox，也不发布 `edge/alarm`。
- EMS 1.0 的 `products/ems/stationary/1.0/scada/base-project/alarms.json` 当前为空，因此没有同类本地规则。

| 消防探测器 | `310040..310044` 温度/烟雾/CO/H2/VOC 屏蔽 | 屏蔽是维护状态，不宜默认按严重故障处理；可作为提示级状态 |
| LED 屏显 | `4540..4551` 故障/告警显示寄存器 | 这些点属于屏显数据，不能仅凭名称认定为设备真实故障源 |
| DIDO 输出 | `985` 断路器跳闸、`986` 故障指示灯 | 当前是可写 DO，不应把输出命令值当成设备故障反馈 |
| 设备在线点 | `read.dataType=device_online` | 采集成功为 1，通信异常为 0；默认只作为状态和变位，不是告警 |

PCS、BMS、液冷和消防的汇总故障字目前没有完整拆位。平台若需要显示具体触发原因，应优先在设备模板中把厂家故障字拆成稳定语义的二值点，再给二值点配置 `alarms[]`，不要只在平台临时解释原始整数。

## 6. EMS、AGC/AVC 和并机状态

这些模块会产生状态点、计算点和反馈校验点，但当前没有直接发布告警的代码路径。

| 来源 | 状态或值 | 触发原因 | 当前输出方式 |
| --- | --- | --- | --- |
| Graph EMS `feedbackVerify` | `1` | 反馈与目标差值在容差内 | 虚拟点 |
| Graph EMS `feedbackVerify` | `0` | 已下发，仍在等待反馈且未超时 | 虚拟点 |
| Graph EMS `feedbackVerify` | `-1` | 反馈持续不满足，超过 `timeoutMs` | 虚拟点 |
| Graph EMS `feedbackVerify` | `-2` | 目标或反馈不可用 | 虚拟点 |
| AGC/AVC 状态 `720050` | `3=降级` | 可用 PCS 能力不能完全满足目标 | 实时点/变位 |
| AGC/AVC 状态 `720050` | `6=故障保护` | 输入失效，或写回/PCS 反馈连续失败达到限制 | 实时点/变位 |
| AGC/AVC 误差 | `720052/720054` | 调度目标与 PCC 实际有功/无功、电压或功率因数存在偏差 | 计算点 |
| 并机模块 | 主从、在线、选举和调度状态 | 柜间通信、选举或能力分配结果 | 状态文件和共享内存点 |

要把这些状态变成平台告警，需要给对应虚拟点增加 `alarms[]`。当前通用告警只支持高低阈值，不能直接表达 `value == -1` 或 `value == 6`；推荐先生成“反馈超时”“输入不可用”“AGC/AVC 故障保护”等独立 0/1 派生点，再为派生点配置高限告警。

## 7. 不属于告警 Topic 的异常

### 7.1 变位事件

`reportOnChange=true` 的点值变化发布到：

```text
edge/event/change/<machineCode>
```

典型内容包括设备在线/离线、DI 状态、运行状态和 EMS 虚拟状态。变位不是告警，平台可按业务规则将某些变位升级成告警，但不能假设所有变位都是故障。

### 7.2 `edge/status` 运行状态

EventEngine 会发布以下状态事件：

| `event` | 原因 |
| --- | --- |
| `point-update-sequence-gap` | 共享内存点更新序号不连续，EventEngine 会触发全量兜底扫描 |
| `event-engine-scan-failed` | 一次 EventEngine 扫描抛出异常 |
| `alarm-persisted` | 告警已写入本地 SQLite，属于操作状态而不是新告警 |
| `report-on-change` | 本轮发布了变位事件 |

MQTT 控制接收、OTA 接收、outbox 重放和 SCADA 上位机失联安全动作也会发布状态事件。它们用于运行诊断，不应进入业务告警表。

### 7.3 回执和任务状态

| 异常 | 实际通道 |
| --- | --- |
| 点位不可写、index 不存在、写回失败或校验失败 | `edge/command/reply/<machineCode>` |
| OTA 校验、下载、安装或回滚失败 | `edge/ota/reply`、`edge/ota/status` |
| 配置拉取、写回、删除或恢复失败 | 对应 `edge/config/*/reply` |
| IEC103 录波目录、传输或上传失败 | `edge/recording/reply`、`edge/recording/status` |
| 诊断命令失败 | `edge/system/diag/reply` |

### 7.4 通信和服务异常

- Modbus/DL/T 645/IEC 请求超时、CRC 错误和重试失败主要写驱动日志，并把在线点置 0 或点质量置坏。
- CAN 接收超时会保留最近值，同时写 `quality=0`、`stale=true`、`qualityMsg="CAN receive timeout"`。
- MQTT 自身断线时无法实时发布“MQTT 断线告警”；测点事件依靠 outbox，系统监测告警当前默认不持久化。
- 采集驱动或服务进程退出由 systemd 和 journal 反映，SystemMonitor 当前不生成“服务已停止”告警。

## 8. 现场配置和验收方法

### 8.1 确认实际加载范围

```sh
jq -r '.deviceConfigFiles[]' /opt/modbus-gateway/config/runtime/apps/mqtt-service.json
```

逐个检查实际告警规则：

```sh
jq '.. | objects | select(has("alarms")) | select((.alarms | length) > 0) | {index, pointCode, name, alarms}' \
  /opt/modbus-gateway/config/runtime/devices/*.json
```

注意：第二条命令会扫描目录内全部文件，最终仍要和第一条命令的加载清单交叉核对。

### 8.2 监听 MQTT

```sh
mosquitto_sub -h <broker> -p <port> \
  -t 'edge/alarm/<machineCode>' \
  -t 'edge/system/monitor/alert/<machineCode>' -v
```

验收至少覆盖：

1. 正常值进入异常区，收到一次 `active=true`。
2. 告警持续时，测点告警不重复；系统告警按重复间隔发送。
3. 值恢复后，测点规则按 `reportRecovery` 发布恢复。
4. CPU 恢复有 `active=false`，并确认内存、磁盘、4G 当前没有恢复消息。
5. MQTT 断开后产生测点告警，恢复网络后验证 outbox 重放。
6. 使用坏质量和过期点验证平台不会把无效数值当成可信业务告警。

### 8.3 查询本地测点告警库

只有 `persistValue` 非空的规则才有记录：

```sh
sqlite3 /opt/modbus-gateway/data/alarm_events.db \
  'select ts,gateway_code,device_code,point_index,point_code,alarm_type,active,threshold,value,quality,stale,persist_value from alarm_events order by id desc limit 100;'
```

## 9. 当前实现限制和建议补项

| 优先级 | 当前限制 | 建议 |
| --- | --- | --- |
| 高 | 测点告警不屏蔽坏质量和过期值 | 增加 `quality/stale` 门控，并定义通信恢复后的重新判定策略 |
| 高 | 内存、磁盘和 4G 没有恢复消息 | 为每个系统指标维护独立状态机并发布 `active=false` |
| 高 | EMS 2.0 的 37 条本地规则没有平台告警 | 建立统一告警规则模型，由同一配置生成 SCADA 和 EventEngine 规则 |
| 高 | PCS/BMS 故障字没有拆位 | 在厂家模板层拆成具体语义点，保留原始故障字用于追溯 |
| 中 | 系统告警默认没有磁盘断线补传 | 为 `monitor-service` 启用独立 outbox，避免和实时遥测混用 |
| 中 | MQTT 测点告警缺少阈值、等级、名称和描述 | 扩展 payload，同时保持旧字段兼容 |
| 中 | 同一 index 配多个同类型阈值共用状态键 | 状态键加入规则 ID 或阈值，避免规则互相干扰 |
| 中 | 只支持 `high/low` | 增加 `eq/ne/bitSet/maskAny`、延时、滞回和连续样本配置 |
| 低 | `mqttDriver.alarmRules` 仅解析不执行 | 删除过时入口或迁移到统一点位告警模型 |
