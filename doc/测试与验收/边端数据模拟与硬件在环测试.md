# 边端数据模拟与硬件在环测试

> 本文是执行操作手册。整体架构、设计理由、能力边界、测试分层和演进计划见[边端模拟测试整体设计报告](边端模拟测试整体设计报告.md)。

## 1. 目标与边界

测试实验室用于在没有真实从站、需要稳定复现故障或准备批量回归时，验证以下真实链路：

```text
协议模拟设备
  -> 真实采集驱动
  -> 独立共享内存
  -> ComputeEngine / EventEngine
  -> MqttDriver / SystemMonitor
  -> Windows 客户端实时监控与写入
```

测试必须从协议端产生数据。直接向共享内存注入值只能测试后半段，不能替代串口、CAN、TCP、帧解析、超时、重试、退避和写后校验测试。

当前覆盖：

| 协议/模块 | 纯软件模式 | 硬件在环模式 | 故障注入 |
| --- | --- | --- | --- |
| Modbus TCP | 支持 | 物理网口 | 超时、断连、异常、写超时、写后校验失败 |
| Modbus RTU | Linux PTY | USB-RS485 | 同上 |
| DL/T 645-2007 | Linux PTY | USB-RS485 | 同上 |
| CAN | UDP 双向虚拟总线 | USB-CAN，需适配器厂商工具 | 停帧、断连语义、写帧 |
| 本机 DIDO | 伪 sysfs GPIO | 真实 DI/DO 工装 | 文件失效、输入切换 |
| IEC104 | TCP 常驻模拟站 | 物理网口 | 超时、断连 |
| Compute/Event/MQTT | 默认随实验室启动 | 同左 | 源点故障会向后传播 |

IEC103 串口、AM5SE IEC103 网口录波和 IEC104 文件传输尚未纳入常驻实验室。现有 AM5SE IEC103 编解码、主动反连 TCP、总召、录波目录、CFG/DAT 拉取、录波命令通道、HTTPS 分片上传/平台 ACK，以及 IEC104 客户端集成测试已纳入默认 CTest；它们提供确定性软件门禁，但不替代常驻模拟栈和实体设备验收。

## 2. 运行模式

### 2.1 纯软件模式 `virtual`

模拟器和真实驱动运行在同一台 Linux 主机：

- Modbus TCP、IEC104 使用回环 TCP。
- Modbus RTU、DL/T 645 自动创建 PTY，驱动打开 PTY 从端。
- CAN 使用测试专用 UDP 双向虚拟总线，不依赖内核 `vcan`。
- DIDO 使用测试目录中的伪 sysfs 文件。

适用于自动回归、退避验证、写回验证和 Win 客户端联调。

### 2.2 硬件在环模式 `hil`

模拟器运行在 Windows 测试机或协议测试仪，边端运行真实驱动并使用真实接口。

| 协议 | Windows 侧 | 边端侧 | 必查参数 |
| --- | --- | --- | --- |
| Modbus TCP、IEC104 | 物理网口 | `ens0` 至 `ens3` | IP、端口、防火墙 |
| Modbus RTU | USB-RS485 | `/dev/ttySPx` | 波特率、8N1、A/B 线、终端电阻 |
| DL/T 645 | USB-RS485 | `/dev/ttySPx` | 2400、8E1、表地址、A/B 线 |
| CAN | USB-CAN | `can0` 或 `can1` | 500 kbit/s、H/L 线、两端 120 欧姆 |
| DIDO | GPIO/继电器工装 | 真实 DI/DO | 干/湿接点、电平、公共端、取反 |

Windows USB-CAN 没有统一系统 API，`gateway-test-lab-sim.exe` 不直接支持厂商私有驱动。应使用适配器自带工具发送本文定义的测试帧，或使用支持 SocketCAN 的 Linux 测试机。

## 4. 组成

### 4.1 模拟器

`gateway-test-lab-sim` 支持：

- `serve`：Modbus TCP。
- `serve-serial --protocol modbus-rtu`：Modbus RTU。
- `serve-serial --protocol dlt645`：DL/T 645-2007。
- `serve-can`：SocketCAN 周期发帧和写帧接收。
- `serve-can --transport udp_test`：跨 Windows/Linux 的 UDP 虚拟 CAN，保留 CAN ID、扩展帧、RTR、FD 和原始 payload。
- `serve-iec104`：启动链路、总召、遥信、遥测、遥控和时钟同步。
- `normal/ramp/random/boundary` 四种数据场景。
- 25ms 状态文件热加载。

Modbus 支持功能码 `01、02、03、04、05、06、0F、10`。DL/T 645 支持常用电能、电压、电流、功率 DI 读取和写入回读。

### 4.2 默认服务栈

`gateway-test-lab start` 启动：

1. 所选协议模拟器，DIDO 不需要常驻模拟进程。
2. 对应真实采集驱动。
3. `ComputeEngine`，生成 `SIM_COMPUTE_DOUBLE` 派生点。
4. `EventEngine`，扫描变位和告警。
5. `MqttDriver`，默认使用 stdout 发布器，每秒生成全量报文。
6. 独立 `SystemMonitor`，供 Win 客户端直连。

计算点有独立的 `device_compute.json` 元数据配置，确保 ComputeEngine、MqttDriver、SystemMonitor 三个进程对派生 `index` 的解释一致。

### 5.4 协议与连接方式测试矩阵

协议类型和传输连接方式是两个不同维度：协议决定报文如何编码、解析和确认，连接方式决定报文如何到达边端。测试时必须同时记录两者，不能只写“Modbus 测试通过”。例如 Modbus TCP 和 Modbus RTU 可以复用寄存器地址、数据类型、比例和业务名称，但不能复用连接参数，也不能用 TCP 的通过结果代替 RS485 的现场验收。

| 协议 | 连接方式 | 模拟器/测试端 | 边端配置要点 | 可以验证 | 不能由该测试证明 |
| --- | --- | --- | --- | --- | --- |
| Modbus TCP | TCP/IP，以太网 | Windows/Linux TCP 模拟器 | `protocol.type=modbus_tcp`；`protocol.tcp.host`、`port`、超时 | TCP 建连、连接重建、功能码、寄存器解析、批量读取、异常码、写后校验 | RS485 A/B 极性、波特率、校验位、收发切换、终端电阻 |
| Modbus RTU | RS485 串行总线 | Linux PTY，或 Windows COM + USB-RS485 | `protocol.type=modbus_rtu`；`serialPort`、`baudRate`、`dataBits`、`stopBits`、`parity`、帧间隔 | 串口参数、RTU 帧、CRC、总线超时、地址冲突、收发切换、断线恢复 | TCP 路由、防火墙、端口监听、网络重连 |
| DL/T 645-2007 | RS485 串行总线 | Linux PTY，或 Windows COM + USB-RS485 | 表地址、2400/8E1 或设备说明书指定参数、DI 数据项 | 表地址、唤醒/帧格式、BCD、数据项、读写回读、超时退避 | TCP 建连和网络链路质量 |
| IEC104 | TCP/IP，以太网 | Windows/Linux IEC104 模拟站 | TCP 地址和端口、公共地址、信息体地址、总召参数 | STARTDT、S 帧、TESTFR、总召、遥信、遥测、遥控确认和断线重连 | 串口 FT1.2、电气接线和 RS485 信号质量 |
| IEC103 | 串口或 TCP（按具体适配） | 协议测试仪或对应模拟器 | 必须按 IEC103 串口/TCP 模板选择对应传输模式 | FT1.2、保护信息、遥测、参数和异常处理 | 未接入的物理接口、装置现场录波质量 |
| AM5SE IEC103 网口 | 装置主动反连 TCP，并配合 UDP 在线/校时 | AM5SE 装置或专用模拟器 | `am5se_passive_tcp`、监听地址/端口、录波输出目录 | 在线广播、反连、总召、变位/遥测、COMTRADE 文件拉取 | 串口 IEC103 和没有装置主动反连行为的普通 TCP 模拟 |
| CAN | SocketCAN、CAN 控制器回环、UDP 虚拟 CAN 或实体 CAN | Linux、Windows UDP 模拟器、USB-CAN 或现场设备 | CAN 接口/测试传输、波特率、标准/扩展帧、帧 ID、位域 | ID 过滤、位域解码、周期、丢帧、写帧和恢复 | UDP/回环不能证明 CANH/CANL、终端电阻、收发器和现场抗干扰 |

#### 5.4.1 Modbus TCP 与 Modbus RTU 的配置对照

两种连接都使用 Modbus 应用层地址和功能码，但配置必须选择对应模板：

```jsonc
// Modbus TCP：每个从站通过 TCP 地址/端口访问
{
  "protocol": {
    "type": "modbus_tcp",
    "slave": 1,
    "tcp": {
      "host": "192.168.1.100",
      "port": 502,
      "connectTimeoutMs": 1000,
      "timeoutMs": 1000
    }
  }
}
```

```jsonc
// Modbus RTU：多个从站共享串口，通过 slave 地址区分
{
  "protocol": {
    "type": "modbus_rtu",
    "slave": 1,
    "transport": {
      "serialPort": "/dev/ttySP1",
      "baudRate": 9600,
      "dataBits": 8,
      "stopBits": 1,
      "parity": "N",
      "timeoutMs": 300,
      "frameIntervalMs": 20
    }
  }
}
```

点表中的寄存器地址、功能码、字节序、比例和读写权限可以在协议确实一致时复用；`tcp` 和 `transport` 不能互换。RS485 设备改成网口接入时，应新建或切换为 Modbus TCP 通道，并重新验证端口、网络路由和设备是否实际开放 502 端口；不能只把 `serialPort` 改成 IP 字符串。

### 5.5 连接方式对结果、时延和故障注入的影响

同一个点位在不同连接方式下的采集周期和故障表现可能不同。报告必须记录 `protocol`、`transport`、设备地址、测试端位置和接口参数，否则结果不可复现。

| 测试层级 | 典型连接 | 能证明什么 | 不能证明什么 | 失败时优先检查 |
| --- | --- | --- | --- | --- |
| L0 配置解析 | 无外部连接 | JSON 字段、点表、地址、权限、索引和启动参数正确 | 任何实际报文和物理链路 | 配置类型、字段名、点表地址和重复 index |
| L1 纯软件协议模拟 | TCP 回环、PTY、UDP 虚拟 CAN、伪 GPIO | 真实驱动调度、报文解析、共享内存、质量传播、MQTT 和实时监控 | 物理接线、电气质量、交换机和 USB 转换器 | 模拟器日志、驱动日志、共享内存点时间戳 |
| L2 主机接口模拟 | Linux PTY、SocketCAN/控制器回环、真实本机 GPIO | 操作系统接口、串口/SocketCAN 调用和本机驱动 | 现场总线、电缆、终端电阻和外部设备 | 设备节点、接口状态、权限、收发计数 |
| L3 Windows 硬件在环 | TCP 网口、COM + USB-RS485、USB-CAN | Windows 测试工具到边端之间的实际传输和协议闭环 | 现场安装距离、EMI、长期负载和现场供电 | Windows 适配器驱动、IP/防火墙、串口参数、A/B 或 CANH/CANL |
| L4 现场物理链路 | 真实网口、RS485、CAN、GPIO | 该设备、该端口、该接线和该参数可用于现场运行 | 其他端口、其他厂家设备和另一种传输模式 | 接线、终端、电平、地址冲突、设备占用和供电 |
| L5 上层业务联调 | 任一已通过的采集链路 + MQTT/Win/平台 | 业务名称、告警、写回、策略和监控展示闭环 | 未经过的底层链路 | 语义映射、质量、时间戳、写后校验和服务日志 |

连接方式会改变测试指标的含义：

- TCP 延迟主要由建连/重连、网络往返、从站处理和应用超时组成；回环 TCP 的延迟不能代表交换机、路由和现场网线延迟。
- RTU 延迟还包括串口发送字节时间、帧间隔、RS485 收发方向切换和同一总线其他从站占用。提高轮询频率前必须确认波特率、请求长度和总线占用率。
- TCP 的断连注入应覆盖主动关闭连接、端口拒绝、网络不可达和服务端重启；RTU 的断连注入应覆盖拔线、从站无响应、CRC 错误、地址不存在、波特率错误和校验位错误。两者故障命令不能互相替代。
- CAN UDP/控制器回环能够验证帧编码和解析，但不能代表实体总线错误计数；实体 CAN 测试还必须验证 CANH/CANL、共地、终端电阻和接口状态。
- PTY 能验证串口读写代码和帧解析，不能验证 USB-RS485 芯片、A/B 极性、隔离、电平和现场干扰。COM + USB-RS485 硬件在环比 PTY 更接近现场，但仍不等于现场验收。
- 伪 GPIO 只能验证逻辑和文件链路。只有真实 DI/DO 工装才能验证干接点、湿接点、公共端、有效电平、取反和 DO 输出。

#### 5.5.1 通用端到端时间模型

不要把 `collect.defaultIntervalMs` 直接当成一次报文完成时间。采集周期是调度目标，实际完成时间还要受到传输介质、设备响应和请求数量限制。单次请求和一轮采集分别按下面估算：

```text
T_request = T_transport + T_device + T_retry + T_queue
T_cycle   = T_schedule + SUM(T_request_i) + T_parse_store + T_delivery
```

其中：

- `T_transport`：报文在线路、TCP 栈或 CAN 总线上的传输时间。
- `T_device`：从站收到完整请求到开始返回的处理时间，以及协议确认/窗口等待。
- `T_retry`：重试带来的附加时间；没有发生重试时为 `0`。
- `T_queue`：同一串口、CAN 总线或驱动写队列等待其他任务的时间。
- `T_schedule`：采集线程实际被调度的时间，不等于配置周期；至少要用单调时钟测量。
- `T_parse_store`：解码、质量计算、写共享内存的时间。
- `T_delivery`：到 MQTT、SystemMonitor 或 Windows 客户端的处理和网络时间；只验收采集驱动时可单独列出，不要混入协议线速。

一轮采集的理论下限是所有串行请求耗时之和；同一条 RS485 总线和同一个 CAN 总线不能把多个请求简单按 CPU 多线程并行相加。不同串口、不同 TCP 连接是否可以并行，必须以实际驱动的调度模型和日志时间戳为准。

验收时至少记录四个时间戳：发送开始 `t_send`、发送结束 `t_tx_end`、收到完整响应 `t_rx_end`、点写入共享内存 `t_store`。由此计算：

```text
T_wire_or_socket = t_tx_end - t_send
T_response       = t_rx_end - t_tx_end
T_driver         = t_store - t_send
T_freshness      = now - pointTimestamp
```

不要用墙上时间计算同一请求的耗时；跨 Windows、边端和设备的墙上时钟可能不一致。跨主机链路需要使用单调时钟或统一 `traceId`，否则只能分别报告各端耗时。

#### 5.5.2 Modbus RTU/RS485 计算

RTU 的一个字符时间由串口格式决定：

```text
T_char_ms = 1000 x (1 + dataBits + parityBits + stopBits) / baudRate
T_frame_ms = frameBytes x T_char_ms
T_gap_ms >= 3.5 x T_char_ms
```

`parityBits` 在无校验时为 `0`，偶校验/奇校验时为 `1`。Modbus RTU 一次读请求的估算值为：

```text
T_rtu_read = T_request_frame
           + T_gap
           + T_device
           + T_response_frame
           + T_gap
           + T_turnaround
```

以读保持寄存器为例，请求帧通常为 8 字节，读取 `N` 个 16 位寄存器时响应帧通常为 `5 + 2N` 字节。因此：

```text
T_rtu_read_ms ~= (8 + 5 + 2N) x T_char_ms
              + 2 x T_gap_ms
              + T_device
              + T_turnaround
```

实际使用的帧间隔应取协议最小值和驱动配置值中的较大者：

```text
T_gap_effective = max(3.5 x T_char, configured frameIntervalMs)
```

如果配置没有 `frameIntervalMs`，按协议最小帧间隔和驱动默认值执行；具体生效值以驱动报文时间戳为准。

这个公式是线速下限估算，实际值还要加入 USB-RS485 驱动、内核调度、收发方向切换、重试和总线被其他从站占用的时间。

**计算示例：9600 8N1、读取 32 个寄存器**

```text
T_char       = 10 / 9600 s = 1.042 ms
T_request    = 8 x 1.042   = 8.33 ms
T_response   = (5 + 64) x 1.042 = 71.88 ms
T_gap        >= 3.5 x 1.042 = 3.65 ms
```

如果从站处理时间为 2ms、收发切换为 1ms，则一次请求约为：

```text
8.33 + 3.65 + 2 + 71.88 + 3.65 + 1 = 90.51 ms
```

同一串口有 3 个从站、每个从站 2 个这样的请求时，仅线速和设备处理时间约为 `6 x 90.51 = 543.06ms`，所以把采集周期填写为 200ms 并不能让这一轮在 200ms 内完成。应减少请求帧、扩大连续寄存器批量、提高波特率、拆分到多个串口，或把目标周期调整到可实现值。`maxRequestRegisters` 不能超过设备说明书和驱动能力，否则响应异常会抵消批量优化收益。

如果配置了重试，估算上限可写成：

```text
T_rtu_with_retry <= T_rtu_read x (1 + retryCount)
                 + backoffDelay
```

轮次退避不应乘进每一帧的正常周期，而应单独记录为该从站下一次被探测前的跳过时间。正常点新鲜度、失败探测间隔和恢复时间必须分开统计。

#### 5.5.3 Modbus TCP/IP 计算

Modbus TCP 没有 RTU 的 3.5 字符静默间隔和串口字节线速约束。连接保持时，一次事务可以按下面估算：

```text
T_tcp_read = T_socket_queue
           + T_network_RTT
           + T_device
           + T_tcp_payload
           + T_parse_store
```

其中 `T_network_RTT` 是边端到设备的实际往返时间；`T_tcp_payload` 通常远小于设备处理时间和网络往返，但低速网络、代理、VPN 或拥塞时不能假设为 0。首次连接或断线重连要另外加上：

```text
T_reconnect = DNS/route + TCP_connect + TLS_handshake(如有) + protocol_startup
```

连接保持时 `T_reconnect` 不应加到每个正常事务中；连接断开后，它会成为恢复时间的一部分。TCP 设备多个请求能否并发，取决于从站是否允许多个未完成事务、驱动是否按序发送以及事务 ID 管理，不能因为 TCP 没有串口间隔就默认并发。

**与上面的 RTU 算例对比**

假设 TCP 连接已建立，测得网络 RTT 为 2ms、设备处理为 3ms、解析和落库为 1ms，则同一批 32 个寄存器的单次事务约为：

```text
T_tcp_read ~= 2 + 3 + 1 = 6ms
```

如果 3 个设备各有 2 个请求，顺序发送约 `6 x 6 = 36ms`，理论上可以放入 200ms 目标周期；但这只证明当前 TCP 网络和设备响应满足该目标，不能反推 9600 8N1 的 RS485 也满足。测试报告必须同时写出实测 RTT、设备处理时间、是否重连和请求是否并发。

#### 5.5.4 DL/T 645、IEC、CAN 和 DIDO 的计算差异

| 协议/连接 | 时间计算重点 | 与同协议其他介质的区别 |
| --- | --- | --- |
| DL/T 645 / RS485 | 与 RTU 相同先算字符时间，再加唤醒字节、帧间隔、表处理时间和 BCD 解码时间；`wakeupBytes` 每增加 1 字节，就增加一个 `T_char` | 不能用 TCP 的 RTT 估算替代表地址、2400/8E1 和 RS485 帧时间 |
| IEC103 / 串口 | 按 FT1.2 帧长度和串口字符时间计算，并加入链路确认、轮询窗口和总召顺序 | IEC103 网口/TCP 没有串口线速，但仍受链路确认和装置处理时间约束 |
| IEC104 / TCP | 按 TCP RTT、装置处理、`t1` 确认窗口和 K/W 窗口计算；自发上送点不等待轮询 | 不能把 IEC104 的自发上送延迟当作 IEC103 串口轮询延迟 |
| CAN / 实体总线 | `T_frame ~= (有效位 + 填充位 + 帧间隔) / bitrate`；还要加仲裁等待和总线占用 | UDP/回环没有真实仲裁、错误帧和收发器延迟，只能测软件传输和解码 |
| CAN / UDP 虚拟总线 | `T_udp ~= UDP RTT + OS 调度 + 模拟器处理` | 不能用 UDP 延迟计算实体 CAN 的帧周期或总线容量 |
| DIDO / GPIO | `T_point ~= 扫描周期 + 去抖窗口 + GPIO 读写时间` | 伪 sysfs 的文件操作时间不能代表真实电平稳定时间和继电器动作时间 |

对于 CAN，理论帧时间受标准帧/扩展帧、DLC、位填充、仲裁和 CAN-FD 数据段影响，优先使用 CAN 分析仪的 `txTimestamp/rxTimestamp` 计算；不能只用配置的 `bitrate` 除以 payload 字节数。对于 IEC104，`t0/t1/t2/t3` 是连接、确认和空闲保活边界，不是每个点的固定采集周期。

#### 5.5.5 周期可达性和报告门限

对每条链路先计算理论忙时：

```text
U_link = SUM(T_request_i + T_gap_i + T_retry_i) / targetCycle
```

当 `U_link >= 1` 时，目标周期在该链路上理论不可达；即使小于 1，也要为设备抖动、系统调度、故障重试和共享内存处理预留余量。建议生产测试使用：

```text
U_link <= 0.70       正常目标
0.70 < U_link < 0.90 需要记录风险并观察 P95/P99
U_link >= 0.90       不作为稳定周期通过
```

报告至少分别给出：

- `configuredCycleMs`：配置的目标周期。
- `estimatedMinimumCycleMs`：按上述公式计算的线速/协议下限。
- `measuredCycleP50/P95/P99`：实测一轮完成周期。
- `measuredFreshnessP95/P99`：点位从设备报文到当前观察时刻的新鲜度。
- `retryAddedMs`、`backoffSkippedCycles`：重试和轮次退避额外增加的时间。
- `transport`：`tcp`、`rs485`、`can`、`udp_test`、`pty` 或 `gpio`，不能省略。

当配置周期小于理论下限时，dry-run 应提示“目标周期不可达”，运行测试也应把它判定为调度违约，而不是简单把点位标记为“协议失败”。

### 5.6 协议与连接方式的操作链路

每次测试按下面顺序执行，并在报告中保留对应证据：

1. **确认协议**：从设备说明书确认是 Modbus、DL/T 645、IEC、CAN 还是 DIDO；不要因“都有地址/状态点”而混用模板。
2. **确认连接**：记录 TCP、RS485、CAN、GPIO 或虚拟接口；记录端口、串口设备、波特率/校验、CAN 波特率或 GPIO 映射。
3. **选择同连接模拟方式**：TCP 选 TCP 模拟器，RS485 选 PTY/COM + USB-RS485，CAN 选 UDP/SocketCAN/USB-CAN，DIDO 选伪 sysfs/真实工装。
4. **先做 L0/L1**：验证配置能启动、点表能解析、正常数据能进入共享内存，确认点名、质量、时间戳和比例正确。
5. **再做连接专项故障**：按 5.5 的故障集合注入，观察驱动错误、单设备隔离、轮次退避、质量变坏和恢复时间。
6. **再做写入闭环**：只对明确可写点执行；检查排队、设备写入、写后回读、超时和失败原因。TCP 写入和 RTU 写入要分别记录。
7. **最后做 L3/L4**：只有对应物理接口通过硬件在环或现场测试，才能把该连接方式标记为“可现场使用”。
8. **接入上层**：确认共享内存、MQTT、SystemMonitor、Windows 实时监控和平台展示使用同一业务点，不以模拟器日志单独作为最终结论。

### 5.7 测试结论的使用规则

- “Modbus TCP 通过”只表示当前 TCP 地址、端口、点表和 TCP 模拟/现场链路通过，不表示 Modbus RTU 通过。
- “Modbus RTU PTY 通过”只表示驱动、RTU 报文和点表逻辑通过，不表示真实 RS485 接线通过。
- “USB-RS485 硬件在环通过”可以证明测试适配器与边端之间的串行闭环，但仍需现场设备、现场线缆和现场参数复测。
- “CAN 回环通过”或“CAN UDP 通过”不表示 CANH/CANL、终端电阻和实体收发器通过。
- 协议解析通过、物理链路失败时，先排查连接方式和接口参数，不要先修改寄存器、位域或业务映射。
- 点表相同只说明应用层语义可能相同；传输层、设备地址、超时、帧间隔、重试和故障注入结果必须按连接方式独立验收。
- 生产验收记录至少包含：协议、连接方式、设备地址、接口参数、模拟器/真实设备位置、测试层级、正常样本、故障样本、恢复耗时、写回结果和限制说明。

## 9. 一键生成完整报告

`performance` 命令会自行启动隔离测试栈、预热、采样、判定、停止服务并保存证据。一次执行同时生成机器可读 JSON 和中文 Markdown 报告：

```bash
gateway-test-lab performance \
  --protocol modbus-tcp \
  --warmup-sec 60 \
  --duration-sec 600 \
  --output-dir /opt/modbus-gateway/test-lab/reports/modbus-tcp
```

支持 `modbus-tcp`、`modbus-rtu`、`dlt645`、`can`、`dio` 和 `iec104`。需要验证真实 MQTT 网络发布时，额外传入隔离的测试 broker：

```bash
gateway-test-lab performance \
  --protocol modbus-tcp \
  --mqtt-broker tcp://192.168.22.30:1883 \
  --output-dir /opt/modbus-gateway/test-lab/reports/modbus-tcp-broker
```

输出目录结构：

```text
report.md               中文结论、指标、门限和限制
report.json             CI/脚本使用的结构化结果
config/                 本次实际配置快照
raw/                    起止计数、点位样本、资源样本、日志、机器信息和 SHA256
```

报告自动覆盖，JSON 中同时保留本次实际门限：

- 协议请求、响应、错误、帧率和成功率。
- 共享内存更新吞吐、待写积压、点位质量和新鲜度 P50/P95/P99/最大值。
- Compute 周期、违约、失败、规则吞吐、输出数、扫描分位数和确定性结果校验。
- MQTT 扫描分位数、周期违约、失败和全量发布达成率。
- Modbus TCP/RTU 虚拟模式的专用序列证据：源事件到共享内存、共享内存到 MQTT 发布调用、源事件到 MQTT 发布调用的 P50/P95/P99。
- 服务存活、归一化 CPU、RSS、RSS 增长和文件描述符分位数。

默认门限为协议成功率 `>= 99.9%`、好质量 `>= 99.9%`、点新鲜度 P95 `<= 1500ms`、Compute/MQTT 扫描利用率 `<= 70%`、MQTT 全量达成率 `>= 95%`、CPU P95 `<= 70%`、RSS 增长 `<= 10240KiB`。所有门限均可通过同名命令参数覆盖；设置 `--expected-frame-rate` 后还会判断调度达成率。HIL 和 DIDO 没有模拟器请求/响应计数时，报告明确标记“未自动计数”，协议成功率不参与判定，但点位链路、质量、新鲜度和上层服务仍参与判定。

退出码：

| 退出码 | 含义 |
| ---: | --- |
| `0` | 所有启用检查通过，报告结论为 `PASS` |
| `1` | 测试执行完成但至少一项未达门限，或运行链路失败 |
| `2` | 参数无效 |

默认在报告生成后停止测试服务；只有显式使用 `--keep-running` 才保留运行状态。Modbus TCP/RTU 虚拟模式使用地址 `65000` 的实验室专用单调序列点，精确关联模拟设备、真实驱动、共享内存和 MQTT 发布调用，不修改生产共享内存 ABI。该证据的范围是 `simulator-to-mqtt-publisher`；未经过外部 broker 和 Win 客户端时，`traceIdAvailable` 保持为 `false`，不能当成完整 T1-T7。其他协议仍只报告共享内存点时间戳到测试程序观察时刻的新鲜度。未接入真实 broker 时，MQTT 结论只覆盖边端内部扫描、组包和全量生成，不代表网络发布确认。

### 9.1 协议与介质时间估算

`performance` 会根据本次 `protocol` 和 `mode` 在 `report.json.timing` 中输出理论时间，并把独立证据写到 `raw/timing-estimate.json`。默认参数来自实验室模板，现场报告应用实测参数显式覆盖：

```bash
gateway-test-lab performance \
  --protocol modbus-rtu \
  --mode hil \
  --timing-operation-count 6 \
  --timing-registers-per-request 32 \
  --timing-retry-count 2 \
  --timing-device-response-ms 2 \
  --timing-parse-store-ms 1 \
  --output-dir /opt/modbus-gateway/test-lab/reports/modbus-rtu-hil
```

其他可选覆盖包括网络 RTT、Socket 排队、链路 Mbps、RS485 收发切换、请求/响应字节数、CAN 波特率/载荷和 GPIO 去抖/读写时间，参数名分别为：

```text
--timing-network-rtt-ms       --timing-socket-queue-ms
--timing-link-mbps            --timing-turnaround-ms
--timing-request-bytes        --timing-response-bytes
--timing-can-bitrate          --timing-can-payload-bytes
--timing-debounce-ms          --timing-io-operation-ms
```

`timing` 对象至少包含 `configuredCycleMs`、`operationTimeMs`、`estimatedMinimumCycleMs`、`worstCaseCycleMs`、`linkUtilizationPercent`、`recommendedCycleMs`、`verdictZh` 和 `physicalMediaTestMode`。这些值是公式估算，不是伪造的 P95/P99 实测值。

在 Win 端打开“设备维护 -> 协议测试 -> 实测报告”，可直接导入 `report.json`。Win 端会同时显示理论周期、链路占用、新鲜度、成功率，以及“仅观察新鲜度 / 边端内部序列 / 完整 T1-T7”证据等级；存在内部序列时还会显示三个阶段的 P95。报告参数不会自动写回生产配置。

- DL/T 645 读取、写入回读、异常和恢复。
- DIDO 输入切换。
- UDP 虚拟 CAN 遥测、停帧故障、恢复和写帧回传。
- IEC104 周期数据和 select/execute 遥控。
- AM5SE IEC103 编解码、主动反连 TCP、总召、录波目录与 CFG/DAT 拉取。
- IEC103 录波命令幂等、文件准备、HTTPS 分片续传与平台 ACK。
- IEC104 客户端总召、遥信/遥测、控制确认和链路恢复集成测试。
- Compute 派生点跨进程可见。
- MqttDriver 全量报文生成。
- MQTT 三类离线存储在进程重启后的顺序重放、当前消息后置和最终积压清零。
- SystemMonitor 健康、实时点和工程拉取。
- 停止后的进程、共享内存和测试接口清理。

测试实验室通过 `GATEWAY_SYSTEM_MONITOR_SHARED_MEMORY_NAME=gateway_test_lab_system_monitor_<protocol>` 隔离系统监测点，禁止复用生产段 `gateway_point_store_system_monitor`。Linux 新建共享内存段使用 robust 进程共享互斥量，可在持锁进程异常退出后恢复；修复前创建且已锁死的旧段不具备该属性。测试必须使用唯一名称，生产升级则由部署脚本停服后清理旧 `gateway_point_store*` 段，再启动全部服务。

自动 CAN e2e 不依赖 `CAP_NET_ADMIN` 或 `vcan`，普通 Linux 用户即可运行。UDP 虚拟 CAN
只用于软件测试，不能替代实体 CAN 控制器、电气接线和抗干扰验收。

## 11. 验收判定

1. 正常场景全部采集点为 `quality=1`。
2. 单设备故障不能阻塞同链路其他设备。
3. 恢复后在配置的探测轮次内恢复好质量。
4. 可写点只在写权限开启时执行，写后校验结果明确。
5. `SIM_COMPUTE_DOUBLE` 等于所选源点的两倍且质量随源点传播。
6. MqttDriver 日志每秒出现测试 machineCode 的全量快照。
7. Win 实时监控可看到配置点、实时值、质量和中文名称。
8. `stop` 后没有测试进程、UDP 监听端口和 `gateway_test_lab_*` 共享内存残留。
