## 一、管理摘要

当前项目已经建立一套可重复执行、可自动判定、可保留证据的边端测试体系。测试不再只检查某个协议函数，也不再依赖人工观察“界面上似乎有数据”，而是从模拟设备报文开始，经过待发布的真实采集驱动、共享内存、计算与事件服务、MQTT、系统监测，最终到达 Windows 客户端或自动验收脚本。

截至 2026-08-19，已形成以下结果：

| 项目 | 当前结果 | 管理结论 |
| --- | ---: | --- |
| 边端 Linux 原生默认门禁 | `45/45` 通过 | 已具备日常回归和发布阻断能力 |
| 新版 Windows 客户端自动测试 | `475/475` 通过 | 客户端核心服务、页面模型和协议测试能力通过回归 |
| 六协议统一性能报告 | 自动生成并通过门禁 | Modbus TCP/RTU、DL/T 645、DIDO、IEC104、CAN 已有统一报告入口 |
| 协议端到端测试 | 自动执行并通过 | 已覆盖真实驱动、共享内存和主要上层服务 |
| 故障与恢复 | 已覆盖主要软件场景 | 可验证单设备故障隔离、坏质量、退避和恢复 |
| 实体接口与现场设备 | 部分具备 | 仍需 USB-RS485、USB-CAN、DIDO 工装和代表性设备完成硬件在环 |
| 外部 MQTT 到 Windows 全链路计时 | 尚未闭环 | 仍需隔离 broker 和客户端统一追踪标识补齐最后两段证据 |

总体判断：**软件级发布门禁已经建立，可以显著降低驱动、配置、共享内存和上层服务之间的集成回归风险；但该结果不能替代实体接口、电气环境、具体厂家设备和长期现场运行验收。**

## 二、为什么建设这套体系

边端产品不是单一驱动程序，而是由多协议采集、共享内存、计算策略、事件处理、MQTT、直连维护和 Windows 工具共同组成。过去只做单点调试时，容易出现以下问题：

1. 协议能够解析，但采集调度没有真正运行。
2. 设备有数据，但比例、单位、质量、时间戳或点位索引错误。
3. 一个从站离线后拖慢整条串口链路，恢复后又不能及时重新采集。
4. Windows 工具显示“写入成功”，但命令没有到达设备或没有完成写后校验。
5. 共享内存已有值，但 MQTT、系统监测或 EMS 计算读取的是另一套索引。
6. 测试借用了生产 machineCode、端口或共享内存，造成测试数据污染生产环境。
7. 问题只在现场出现，缺少相同输入和完整证据，无法稳定复现。

本次设计的核心目的，是把这些跨模块风险提前到研发和发布阶段发现，并让同一个故障能够重复执行、自动判定和追踪原因。

## 三、建设目标

### 3.1 业务目标

- 降低新驱动、新点表和新配置上线后影响已有项目的风险。
- 减少必须到现场、连接真实设备后才能发现的软件问题。
- 为版本发布提供统一、客观、可追溯的准入依据。
- 让边端、Windows 客户端和后续平台测试使用同一套指标与证据口径。
- 支持厂家模板、项目配置和协议版本长期复用，而不是依靠个人经验验收。

### 3.2 技术目标

- 测试输入从协议边界产生，采集侧使用待发布的真实驱动。
- 支持正常、变化、边界、断连、超时、错误帧和恢复场景。
- 验证采集、质量传播、共享内存、计算、事件、MQTT 和实时监控链路。
- 自动输出中文报告、结构化 JSON、配置快照、原始日志和校验摘要。
- 测试环境与生产 machineCode、topic、端口和共享内存隔离。

## 四、总体测试架构

```text
协议模拟设备 / 实体设备
          |
          v
待发布的真实采集驱动
          |
          v
隔离共享内存与点位路由
          |
          +--> ComputeEngine / EMS 计算
          +--> EventEngine / 告警与变位
          +--> MqttDriver / 全量、实时、补传
          +--> SystemMonitor / 维护与诊断
                              |
                              v
                  Windows 客户端 / 自动验收脚本
```

架构分为四个部分：

| 部分 | 作用 | 设计原因 |
| --- | --- | --- |
| 设备模拟层 | 按真实协议生成数据和故障 | 直接写共享内存无法验证协议、超时、重试和退避 |
| 生产运行层 | 使用待发布驱动和服务 | 保证通过的是准备发布的程序，而不是测试替身 |
| 测试控制层 | 启停、切换场景、注入故障 | 让同一问题可以重复执行，减少人工偶然性 |
| 证据与判定层 | 计算指标、判定结果、保存报告 | 防止只凭界面截图或单条日志得出结论 |

## 五、测试分层与发布含义

| 层级 | 测试内容 | 当前状态 | 可以证明 | 不能证明 |
| --- | --- | --- | --- | --- |
| L1 配置与编解码 | 配置校验、协议字段、CRC、字节序 | 已具备 | 单模块输入输出正确 | 完整进程链路可运行 |
| L2 组件测试 | 驱动客户端、共享内存、路由、MQTT 队列 | 已具备 | 核心组件行为正确 | 多进程组合没有问题 |
| L3 软件端到端 | 模拟器、真实驱动、共享内存 | 已具备 | 采集、故障、恢复和写回软件链路 | 实体电气接口已通过 |
| L4 服务链路 | Compute、Event、MQTT、SystemMonitor | 已具备 | 数据能被主要上层服务正确消费 | 外部平台和公网链路已通过 |
| L5 Windows 联调 | 工程、名称、质量、协议报告、写入交互 | 部分具备 | 客户端核心逻辑和导入流程正确 | 外部 broker 到界面完整时延 |
| L6 硬件在环 | USB-RS485、USB-CAN、GPIO 工装、实体网口 | 待补齐 | 实体接口和接线闭环 | 所有厂家设备均兼容 |
| L7 现场验收 | 真实设备、线缆、干扰和持续运行 | 按项目执行 | 当前项目组合可交付 | 其他项目自动继承结论 |

发布时必须按层级描述结论。例如，“Modbus RTU 软件端到端通过”不能简写成“现场 485 已通过”；“CAN UDP 模拟通过”不能替代 CANH/CANL、终端电阻和错误帧验收。

## 七、测试指标与判定机制

测试工具采用“默认门限 + 项目可覆盖”的方式，既保证统一基线，也保留特殊项目的调整空间。

| 指标 | 默认门限 | 管理含义 |
| --- | ---: | --- |
| 协议成功率 | `>= 99.9%` | 正常测试窗口内请求和响应稳定 |
| 好质量点比例 | `>= 99.9%` | 点位不是靠旧值或错误质量维持 |
| 点位新鲜度 P95 | `<= 1500ms` | 绝大多数点在目标时间内更新 |
| Compute/MQTT 扫描占用 | `<= 70%` | 为抖动、重试和扩容保留余量 |
| MQTT 全量发布达成率 | `>= 95%` | 周期上送基本按计划执行 |
| CPU P95 | `<= 70%` | 边端仍保留运行余量 |
| 测试窗口 RSS 增长 | `<= 10240KiB` | 防止明显持续内存增长 |

理论估算、软件实测、硬件在环和现场验收分别记录，不能用理论值冒充实测值。报告中的每个结论都应带证据等级；没有统一追踪标识时，只报告观察到的新鲜度，不推算一条报文的完整端到端时间。

## 八、时间计算方法与证据口径

时间指标分为三类，三者回答的问题不同：

| 类型 | 回答的问题 | 数据来源 | 使用阶段 |
| --- | --- | --- | --- |
| 理论时间 | 当前配置在物理和协议上是否可能达到目标周期 | 波特率、帧长度、请求数、RTT、设备响应等输入 | 配置设计和测试前评审 |
| 实测时间 | 待发布程序在本次环境中实际运行多快 | 模拟器、驱动、共享内存、服务日志和单调时钟 | 软件 E2E、HIL 和性能门禁 |
| 端到端时间 | 一条数据从设备产生到客户端显示经过多久 | 同一追踪序列或统一时钟的分段时间戳 | 系统联调和现场验收 |

### 8.1 通用轮次计算

先计算一轮需要执行的操作数：

```text
操作数 N = 设备数 x 每设备请求数（或每设备帧数）
正常轮次时间 = 单次操作时间 x N
最坏重试轮次 = 正常轮次时间 x (1 + 重试次数)
正常链路占用率 = 正常轮次时间 / 目标周期 x 100%
最坏链路占用率 = 最坏重试轮次 / 目标周期 x 100%
建议周期 = 向上取整(正常轮次时间 / 70%)
```

这里的“轮次时间”是同一链路顺序执行完本轮请求所需时间，不是 MQTT 上送周期，也不是界面刷新时间。轮次退避产生的“跳过若干轮后再探测”单独记录，不重复乘入每一帧的正常时间。

统一判定口径为：

| 条件 | 结论 | 含义 |
| --- | --- | --- |
| 正常占用 `<= 70%` 且最坏占用 `< 100%` | 可进入实测 | 至少保留 30% 的调度和抖动余量 |
| 正常占用 `> 70%` 或最坏占用 `>= 100%` | 有风险 | 需要实测 P95/P99，并评估重试积压 |
| 正常占用 `>= 90%` | 不可稳定运行 | 正常链路已基本没有故障恢复余量 |

### 8.2 串口协议时间计算

Modbus RTU、DL/T 645 和串口 IEC103 先按串口格式计算一个字符的传输时间：

```text
每字符位数 = 1 个起始位 + 数据位 + 校验位 + 停止位
字符时间(ms) = 1000 x 每字符位数 / 波特率
帧时间(ms) = 帧字节数 x 字符时间
```

一次串口请求/响应的理论时间为：

```text
单次操作时间 = (唤醒字节 + 请求字节 + 响应字节) x 字符时间
             + 2 x 有效帧间隔
             + 设备响应时间
             + 收发切换时间
             + 解析落库时间

有效帧间隔 = max(协议最小间隔, 配置帧间隔)
```

对于 Modbus RTU，协议最小间隔取 `3.5 x 字符时间`；读 `R` 个 16 位寄存器时，请求通常为 `8` 字节，响应通常为 `5 + 2R` 字节。DL/T 645 还要加入前导唤醒字节，常见串口参数为 `2400/8E1`，但最终必须以设备说明书为准。IEC103 串口还需结合链路确认和总召顺序，理论公式只用于容量规划。

### 8.3 TCP 协议时间计算

Modbus TCP、IEC103 TCP 和 IEC104 在连接已经建立时按以下方式计算：

```text
单次操作时间 = Socket 排队时间
             + 网络往返时间 RTT
             + 设备响应时间
             + 请求/响应载荷链路传输时间
             + 解析落库时间

载荷链路时间(ms) = (请求字节 + 响应字节) x 8 / 链路速率(bit/s) x 1000
```

正常长连接不把 TCP 建连时间重复计入每次请求；首次连接和断线恢复应另外记录 DNS、路由、TCP 建连、TLS 握手（如有）和协议启动时间。IEC104 的 `t0/t1/t2/t3` 是连接、确认和保活边界，不是每个点的固定采集周期；设备自发上送的数据要单独统计。

### 8.4 CAN 和虚拟 CAN 时间计算

实体 CAN 的单帧理论时间按帧位数和波特率估算：

```text
未填充位数 = 基础帧位数 + 数据字节数 x 8 + 帧间隔位
估算总位数 = 未填充位数 x 1.20
单帧时间(ms) = 估算总位数 / CAN 波特率 x 1000
```

标准帧基础位数按 `47` 位、扩展帧按 `67` 位估算，`1.20` 用于预留位填充。该结果不包含真实总线仲裁等待、错误帧和重发，正式 HIL 应以 CAN 分析仪的发送/接收时间戳为准。

UDP 虚拟 CAN 只按“UDP 单程时间 + Socket 排队 + 测试帧链路时间 + 软件处理时间”计算，用于验证软件传输与解码，不能用于证明实体 CAN 总线容量。

### 8.5 DIDO 时间计算

DIDO 必须区分“处理占用”和“状态确认延迟”：

```text
本轮处理占用 = 点数 x 单点 GPIO 读写时间
最坏状态确认延迟 = 扫描周期 + 去抖窗口 + 本轮处理占用
链路占用率 = 本轮处理占用 / 目标周期 x 100%
```

扫描等待和去抖窗口不持续占用 CPU，不能把它们加到处理占用后再计算链路利用率，否则会把合法配置错误判断为接近或超过 100%。

### 8.6 Modbus RTU 与 TCP 对比例子

以 `3` 台设备、每台 `2` 个请求、每次读取 `32` 个寄存器为例：

| 参数 | Modbus RTU | Modbus TCP |
| --- | ---: | ---: |
| 连接参数 | `9600/8N1` | `100Mbps`、RTT `2ms` |
| 设备响应 | `2ms` | `3ms` |
| 收发/解析 | 收发切换 `1ms` | 解析落库 `1ms` |
| 单次理论时间 | 约 `90.5ms` | 约 `6.0ms` |
| 6 次请求正常轮次 | 约 `543ms` | 约 `36ms` |
| 目标周期为 `1000ms` 时占用 | 约 `54.3%` | 约 `3.6%` |
| 按 70% 余量建议周期 | 不小于约 `776ms` | 不小于约 `52ms` |

这个例子说明相同点表和请求数量，在不同传输介质上的可达周期差异很大。TCP 测试通过不能推导 RS485 也能达到相同周期；提高 RTU 采集速度通常需要提高设备支持的波特率、合并连续寄存器、减少请求数或拆分串口。

### 8.7 端到端 T1-T7 分段计时

完整数据链定义七个时间点：

| 时间点 | 含义 |
| --- | --- |
| `T1` | 模拟器或真实设备生成报文 |
| `T2` | 驱动收到并完成协议解析 |
| `T3` | 驱动写入共享内存 |
| `T4` | ComputeEngine/EventEngine 完成处理 |
| `T5` | MqttDriver 或 SystemMonitor 读取并发出 |
| `T6` | Windows 客户端或平台收到 |
| `T7` | Windows 客户端或平台完成界面刷新 |

据此计算：

```text
协议采集时延 = T3 - T1
计算处理时延 = T4 - T3
边端上送时延 = T5 - T4
网络接收时延 = T6 - T5
界面刷新时延 = T7 - T6
端到端可见时延 = T7 - T1
```

当前 Modbus TCP/RTU 通过专用单调序列点可以给出 `T1-T3`、`T3-T5` 和 `T1-T5` 的 P50/P95/P99；DL/T 645、DIDO、IEC104 和虚拟 CAN 当前只报告点位新鲜度，不把不同报文的相近时间戳拼成完整链路。外部 broker 和 Windows 客户端贯通统一追踪标识后，才能正式给出 `T6/T7` 和完整 `T1-T7`。

### 8.8 统计和时钟规则

- 预热阶段不计入正式样本，正式窗口内分别输出 P50、P95、P99 和最大值。
- 同一进程或同一主机优先使用单调时钟计算耗时，避免系统校时导致负数或跳变。
- 跨主机直接相减墙上时间前，必须确认时钟同步误差显著小于目标时延。例如目标为 `200ms` 时，建议主机间误差控制在 `10ms` 以内。
- 时钟误差不满足要求时，使用统一序列/追踪标识和同一时钟的往返时间，不伪造跨主机单向耗时。
- 配置周期、轮次耗时、点位新鲜度、MQTT 周期和界面刷新周期分别统计，不能互相替代。

## 十、发布门禁建议

建议把以下流程设为边端和 Windows 客户端版本发布的固定要求：

1. **构建确认**：记录源码提交、分支、构建机和二进制 SHA256。
2. **默认回归**：边端全部 CTest、Windows 全部自动测试必须通过。
3. **协议回归**：本次修改涉及的协议必须生成对应统一报告并达到门限。
4. **配置验收**：检查 machineCode、meterCode、index、单位、比例、读写权限和业务名称。
5. **硬件在环**：涉及实体串口、CAN、DIDO 或新硬件型号时必须执行对应 HIL。
6. **现场小范围验证**：新厂家、新型号或控制策略先低风险验证，再进入正式运行。
7. **证据归档**：保存 `report.md`、`report.json`、实际配置、原始日志和校验摘要。

以下情况建议直接阻断发布：

- 自动测试存在失败且无正式风险豁免。
- 单设备故障会阻塞同链路其他设备。
- 写入权限、写后校验或控制目标不明确。
- 测试使用的不是待发布二进制。
- 点位编码、索引或业务映射存在重复和错位。
- 报告没有区分软件模拟、硬件在环和现场证据。

## 十一、现存风险与缺口

| 优先级 | 缺口 | 风险 | 建议措施 |
| --- | --- | --- | --- |
| P0 | 外部 broker 到 Windows 客户端缺少统一 T1-T7 证据 | 无法精确区分边端、网络、broker 和界面耗时 | 建隔离 broker，贯通统一追踪标识 |
| P0 | RS485、CAN、DIDO 实体工装不完整 | 软件通过后仍可能在电气层失败 | 建设固定 HIL 台架并纳入发布流程 |
| P0 | 测试脚本仍保留生产二进制回退兼容 | 可能误测旧程序 | 增加严格发布模式，禁止静默回退 |
| P1 | 多协议、多实例并发稳定性不足 | 资源竞争和锁问题可能在组合运行时出现 | 增加并发和长时间压力测试 |
| P1 | IEC103/AM5SE 缺少常驻模拟栈 | 录波和文件链路回归成本较高 | 建常驻模拟服务和录制回放库 |
| P1 | SSH.NET 依赖存在高危漏洞警告 | 增加客户端安全和供应链风险 | 评估兼容版本并升级后回归 |

## 十二、下一阶段建设建议

### 第一优先级：补齐发布闭环

- 建立独立 MQTT 测试 broker，补齐边端到 Windows 的完整计时和断线恢复证据。
- 建立 USB-RS485、USB-CAN 和 DIDO 固定测试工装。
- 增加发布严格模式，确保测试二进制与发布二进制完全一致。
- 完成 SSH.NET 依赖升级和全量回归。

### 第二优先级：提升系统稳定性证据

- 增加 24 小时及更长周期稳定性测试。
- 增加多协议并发、多个共享内存实例和网络切换故障。
- 增加 CPU、内存、文件描述符、共享内存锁等待和 MQTT 积压趋势判定。
- 增加设备断电、边端重启和策略状态恢复场景。

### 第三优先级：形成厂家设备验证资产

- 将厂家点表模板、模拟器配置、边界值和预期结果统一管理。
- 建立脱敏报文录制与回放库。
- 新厂家、新型号接入时自动生成协议测试和回归用例。
- 逐步覆盖 PCS、BMS、电表、温控、消防、DIDO 及 EMS/AGC/AVC 闭环。

## 十三、所需资源与管理决策

建议确认以下事项：

1. 将自动测试和证据归档正式纳入版本发布流程，失败默认阻断发布。
2. 提供固定 Windows 测试机、边端测试机、隔离交换机和 MQTT broker。
3. 配置 USB-RS485、USB-CAN、DIDO 电气工装及代表性厂家设备。
4. 明确边端、Windows、平台和硬件各自的测试负责人及签字边界。
5. 为长期稳定性测试保留持续运行环境，避免与现场调试环境混用。

这部分投入的价值不是增加一套展示系统，而是把现场故障前移为研发阶段可重复、可定位、可阻断的问题，并将个人调试经验沉淀为公司可复用的测试资产。

## 十四、结论

项目当前已经从“依靠人工连接设备验证”进入“软件链路具备自动发布门禁”的阶段。边端 `45/45` 和 Windows 客户端 `475/475` 的结果说明现有核心软件回归基线稳定，六协议统一报告也已具备继续扩展的基础。

下一阶段不应继续堆叠孤立测试脚本，而应集中补齐实体接口、外部 MQTT 到 Windows 的完整证据、并发与长期稳定性，以及厂家模板驱动的自动测试。完成这些工作后，测试体系才能从研发回归工具进一步升级为可支撑批量交付和多厂家设备接入的产品级质量保障体系。
