# 直连维护通道 v2（SystemMonitor）

分支 `feat/maint-v2`，基于 `realese1.0 @ aac6e5e`。接口与授权票格式按客户端交接文档
`GatewayClient/docs/handoff/edge-maintenance-v2.md`（以下简称“交接文档”）实现；与交接文档不同的地方见第 7 节。

## 1. 做了什么

| 能力 | 说明 |
| --- | --- |
| HTTPS | 运行时加载设备上的 OpenSSL（dlopen `libssl` / `libcrypto` 3 或 1.1，与 MQTT TLS、OTA 验签相同做法），**不新增链接依赖**；TLS 1.2+；设备自签证书（ECDSA P-256，CN = 机器码，10 年），客户端按 SHA-256(证书 DER) 指纹固定 |
| 会话 | `POST /api/v2/auth/login {"passwordSha256"}`（与 v1 同一凭据、同一失败锁定）→ 令牌 15 分钟滑动、最长 8 小时；设备只存 SHA-256(令牌)，SystemMonitor 重启后令牌仍有效（直推事务会重启它） |
| 授权票 | Ed25519 验签，验证顺序与拒绝码按交接文档第 4 节；一次性票记到过期为止；12 条测试向量全部通过 |
| 调试模式 | `GET/POST /api/v2/debug-mode`，进入要 `debug.enter` L2 票；30 分钟无请求自动退出；状态文件 `debug-mode.json`（0644，供本地屏幕横幅读取） |
| 配置直推 | `POST /api/v2/config/apply`：`dryRun` 默认 true；预演给 `checks[]` 和 `affectedServices`；正式应用要 `config.apply` L3 票，回 202 + 事务号，**按 requestId 幂等**；事务在独立助手进程里执行：校验 → 备份 → 写入 → 重启 gateway-services → 健康检查（期望单元全部 active 且稳定）→ 提交；不健康自动回退并再重启 |
| 回退 | `POST /api/v2/config/restore {transactionId}`（`config.restore` L3）：进行中的事务先停下再回退（回 202 + 当前状态，客户端接着查询），已提交的事务直接回到应用前的备份；文件在事务之后又被改过时拒绝（409 `restore_conflict`） |
| 写点 | `POST /api/v2/control/batch`：`dryRun` 默认 true，设备预判可写性、量程、步长、允许值、优先控制租约、功率控制归属；正式写要 `control.batch` 票（安全类参数 161/162/151/535/504/453/454/457/458 要 L3）；回执逐点 `accepted / adoptedValue / arbitrationLevel / rejectReason / stage / writebackTs / readback`；请求里出现 `highPriority / priority / priorityControl` 一律 400 `high_priority_not_allowed`，`source` 由设备固定 |
| 按点读 | `POST /api/v2/points/query {indexes, meters}`、`GET /api/v2/telemetry/full`：带 `total` / `truncated`，非数值输出 `null` 且 `quality=0`，**不碰上位机心跳租约** |
| 设备审计 | `audit.jsonl` 只追加、哈希链：`hash = SHA-256(prevHash + JCS(本条去掉 hash))`，首条 `prevHash` 为 64 个 0；`GET /api/v2/audit?sinceSeq=&limit=` |
| v1 只读 | v2 启用时（默认 `v1ReadOnly=true`）v1 端口的写接口（control/batch、config/apply 正式应用、config/delete、config/restore、ota/jobs）一律 403 `use_maintenance_v2`：**知道口令不能写** |
| 系统状态 | `GET /api/v2/system/status` 按 `gateway-services.sh list` 的期望单元报状态（修交接文档第 1 节 #7），带 `expected:true` |
| 删除配置（第二阶段） | `POST /api/v2/config/delete {machineCode, requestId, reason, dryRun, paths}`：`dryRun` 默认 true；正式删除要 `config.delete` L3 票，回 202 + 事务号，与直推同一套事务（备份 → 删除 → 重启 → 健康 → 提交，不健康回退时文件放回）。`config/apply` 的 `files[]` 也可带 `{"path", "delete": true}`，与改动一起删（同一事务）。只删运行目录 `apps/`、`devices/`、`logic/` 下的 JSON（不含 SystemMonitor 自己的应用配置和 `device_identity.json`）；删除后若还有运行配置引用它（按路径、相对路径逐字核对所有字符串值，同一请求里改过的文件按新内容算），预演即报 `config.reference` 错误 |
| 服务日志（第二阶段） | `GET /api/v2/logs?unit=&level=&since=&until=&limit=&follow=`（会话令牌，只读）：`journalctl -o json`，单元只能是期望单元加 `gateway-services.service`（其他回 400 `unit_not_allowed`）；`level` 为 emerg…debug 或 0–7；`limit` 1–5000（默认 500）；`follow=true` 时以服务端推送返回（`event: line`，15 秒无输出发 `heartbeat`） |
| 实时推送（第二阶段） | `GET /api/v2/realtime/stream?indexes=&meters=&minIntervalMs=`（只读，与 `points/query` 一样不要令牌、不碰心跳租约）：`text/event-stream`，首个 `points` 事件是全量，之后只推变化的点（值、质量、时间戳、过期标志任一变化），无变化每 5 秒 `heartbeat`；每台设备最多 4 条推送连接（第 5 条回 429 `too_many_streams`），每条最多 5000 点，`minIntervalMs` 100–60000（默认 250） |
| 离线升级（第二阶段） | `POST /api/v2/ota/uploads`（会话令牌）：`X-GZ-Sha256` 必填，包直接写到 `data/maintenance-v2/ota/uploads/`（0600），边收边算 SHA-256（运行时加载的 OpenSSL），不符 400 `sha256_mismatch`；上限 `ota.maxArtifactBytes`，空间按 `ota.minFreeBytes` 留余量；同时只收一个；新上传会删掉没被未结束任务用到的旧上传。`POST /api/v2/ota/jobs`：`dryRun` 默认 true，核对上传的包与任务一致、包类型、任务号、未结束任务、**验签**（v2 总是要签名，与设备 `requireSignature` 无关）、空间，回 `checks[]`；正式任务要 `ota.job` L3 票，先核对票再核对包，都通过才消耗一次性票、回 202。安装由现有 `OtaService` 在助手进程（`systemd-run` 的 `gz-maint-v2-ota-<任务号>`）里执行：与平台 OTA 同一套复制校验、`ota-apply.sh`、重启健康结果与回滚、意图日志与对账。`GET /api/v2/ota/jobs/{id}` 按设备上的 OTA 证据（`ota_final_*`、`health_*`、`health_pending`、状态行）给 `stage`：`accepted → verifying → applying → health-check → completed`，失败 `rolled-back` / `failed`；终态写设备审计 `ota.job/<结果>` 并删掉上传的包。助手进程中断时由 SystemMonitor 接着等结果（`ota-watch`） |
| 拒绝留痕（第二阶段） | 授权票被拒（`malformed`、`level_too_low`、`replayed` 等）也写设备审计：`result = rejected:<拒绝码>`，`target` 为请求的路径或点号 |

`GET /api/v2/identity` 的 `features` 为 `["configDelete", "logs", "mappingStage", "ota", "realtimeStream"]`（客户端按它决定用不用这些接口）。

离线升级的前提：设备上有平台升级公钥（`mqtt-service.json` 的 `ota.signaturePublicKeyPath`，默认 `/etc/modbus-gateway/ota.pub`）且 `ota.enabled=true`；
设备只有一把升级公钥，任务里的 `keyId` 只记录不核对；没有公钥时预演回 `ota_key_unavailable`。

本地屏“调试中”横幅：本地屏程序（`LocalDisplayQtEms`，设备上是 `ky-ems/KY-EMS`）每 2 秒读 `data/maintenance-v2/debug-mode.json`，
调试模式期间在屏幕顶部显示“调试中 · 操作人 … · 原因 … · 自 HH:mm”（不接收触摸；最后操作超过 40 分钟时注明“状态可能未刷新”），
退出后隐藏。文件位置可用 `--maintenance-debug-file` 改。设备上要换本地屏程序才生效（`tools/build_scada_qt_aarch64.sh` 在 22.11 编）。
每次显示 / 隐藏都往 stderr（`ky-ems.service` 的日志）写一行 `maintenance debug banner: shown: … / hidden`，启动时写
`watching <文件> (debug mode not active)`；客户端实机检查用它核对屏幕那边的动作（不用人盯着看）。隐藏时立即重绘横幅覆盖过的区域。
横幅放在屏幕工作区内：桌面顶栏（如 22.7 上 GNOME 的顶栏）压在窗口上沿时，横幅下移到顶栏下面（最多窗口高度的四分之一）。
截屏核对：`/run/ky-ems/banner-snapshot.request` 存在时，每次显示 / 隐藏 1.5 秒后把整个屏幕（含桌面顶栏）存成
`/run/ky-ems/banner-shown.png` / `banner-hidden.png`，日志写 `maintenance debug banner: snapshot <文件> <宽>x<高>`；
没有请求文件就不截。请求文件由实机检查放、取回截图后删。
调试状态的“读—判断—写”在一把锁里做（退出、空闲超时、记录最后操作），请求刷新最后操作时间不会把刚退出的状态写回成“调试中”。

### 测点映射阶段（CQ15，`features` 含 `mappingStage`）

映射文件 `runtime/logic/point-mapping.json`（格式见 `include/edge_gateway/point_mapping.hpp` 头注释与客户端 `formats.md` §7.1），
由工程客户端按型号模板 + 设备实例 + 运行点表生成，随配置直推下发。

- **ComputeEngine 每拍**：① 输入映射——读来源设备点（质量好、未过期、不超前、不超过 `validity.timeoutMs`），多来源按 `aggregate`
  （sum / min / max / avg）合成，`scale`、`offset`、`invert` 换算或 `enum`（设备值 → EMS 数字代码）映射，写 EMS_CORE 的虚拟点
  （680000–689999，`pointCode` 等于虚拟点名）；任一来源无效则虚拟点质量 0（带原因），过期时间同图输出（`graphOutputTtlMs`）。
  ② 策略图。③ 输出映射——读 EMS 输出点（无效则不写、保持设备现值），反算成设备值并按 `write.min/max` 钳位，超出死区或到
  `refreshMs` 时经现有写入路径（功率控制归属、可写性、集群写保护、驱动队列）写设备点，与图共用 `maxWritesPerScan`；
  写后核对驱动写入结果与 `write.readback` 点（容差内为 ok，超时记 `readback-timeout`）。
- **有映射文件时，策略图 `controlWrite` / `pcsWriteback` 只能写 EMS 点**：写设备点被拒（节点错误，计入不健康周期）；没有映射文件的设备照旧。
- 映射与点表不一致时 ComputeEngine 不启动（直推的健康检查失败 → 自动回退）。
- 状态文件 `run/point-mapping-status.json`（`computeEngine.pointMappingStatusFile`）：每条的状态（输入 valid / invalid；输出
  no-command / verifying / ok / readback-timeout / writeback-failed / rejected / enum-miss）、值、最近写入时间、核对失败次数。
- `computeEngine.pointMappingFile` 可改映射文件位置（默认 app 配置所在 `apps/` 的同级 `logic/point-mapping.json`）。
- **预演**（`config/apply`）：请求之后设备上若有映射文件，按 ComputeEngine 将要加载的点表（`mqtt-service.json` 的 `deviceConfigFiles`，
  含本次请求的新内容）核对：虚拟点在 EMS_CORE 且号段、编码对；来源 / 回读点存在且表计与编码一致、不是 EMS 点；输出目标可写、
  同一设备点只由一条输出写（`mapping.points` / `mapping.write` / `mapping.format`）；ComputeEngine 启用时，图里直接写设备点的节点
  逐个报 `mapping.graphWrites`。ComputeEngine 没启用时给提示。
- `enum` 的目标只接受数字代码（EMS 标准枚举名称待 CQ17 定稿）；输出不支持多来源。
- 单元测试 `point_mapping_test`（49 项）：解析与点表核对、换算、图写入目标、输入 / 输出 / 死区 / 刷新 / 回读 / 驱动失败、
  映射启用时图写设备点被拒、ComputeEngine 加载与拒绝不一致的映射。
- 契约测试（客户端 `tst_live_edge_v2b::pointMapping`）：工程模板 + 实例生成映射随直推下发——工程启用 ComputeEngine 且出厂图
  直接写 PCS / 液冷点时预演逐个指出节点；停用 ComputeEngine 后提交成功（提示待启用）；引用不存在的点、重新启用 ComputeEngine 都被预演拒绝。
- **注意**：出厂策略图（shuntong_ems_graph.json）有 14 个直接写设备点的 controlWrite。设备上放映射文件之前，要先把这些节点改成写
  EMS 输出点并配对应的输出映射，否则预演拒绝（ComputeEngine 启用时）。

## 2. 配置

`apps/monitor-service.json` → `systemMonitor.directMaintenance.v2`（不认识的字段旧固件会忽略，可先改配置再换程序）：

```json
"v2": {
  "enabled": true,
  "listenPort": 9444,
  "listenHosts": [],
  "v1ReadOnly": true,
  "sessionTtlSec": 900,
  "sessionMaxSec": 28800,
  "debugIdleSec": 1800,
  "healthTimeoutSec": 90,
  "healthStableSec": 10,
  "maxConnections": 8
}
```

- `listenHosts` 为空时用 v1 的 `listenHosts`；放行网段、失败锁定、口令凭据都与 v1 共用。某个地址绑定失败只跳过该地址。
- 默认端口 9444，与 v1（9443）并存；以后 v1 关闭时可改成 9443。

不在应用配置里、配置直推也改不到的安全锚点（只有 root 能改）：

| 位置 | 内容 |
| --- | --- |
| `/opt/modbus-gateway/config/maintenance-v2/server.crt`、`server.key`（0600） | 设备证书与私钥，`SystemMonitor --init-maintenance-tls` 生成 |
| `/opt/modbus-gateway/config/maintenance-v2/trusted-ticket-keys.json` | 信任的平台公钥：`{"keys":[{"keyId":"…","algorithm":"Ed25519","publicKey":"<32 字节公钥 base64>"}]}`；固件内置列表目前为空（平台正式公钥 C5 下发） |
| `/opt/modbus-gateway/data/maintenance-v2/` | 会话、一次性票、审计、调试模式、事务（`transactions/<id>/tx.json`、`staged/`、`backup/`） |

两个目录可用 `--maintenance-v2-dir`、`--maintenance-v2-state-dir` 改（测试用）。

## 3. 命令

```sh
SystemMonitor --help
SystemMonitor --app-config /opt/modbus-gateway/config/runtime/apps/monitor-service.json --init-maintenance-tls
# 输出：fingerprint=AA:BB:…（95 个字符） 和 certFile=…；已有证书时只输出指纹（幂等）；没有 openssl 命令时输出 unsupported=1
```

证书用设备上的 `openssl req` 生成（私钥文件 0600，不离开设备，不打印）。

## 4. 配置事务的执行方式

- `gateway-services.sh apply` 会停掉并重启 `system-monitor@*`，所以事务不能在 SystemMonitor 里跑：服务端写好事务日志
  （`state: accepted`、暂存内容、写入前文件的 SHA-256）后，用 `systemd-run --unit=gz-maint-v2-apply-<事务号>` 起一个
  `SystemMonitor --maintenance-v2-tx <事务号>` 助手进程（没有 systemd 时双 fork 脱离），助手持有事务锁直到结束。
- 助手：复核内容（边端加载器）与“预演之后文件没被别人改过” → 先记日志再写（备份 → 原子写）→
  `systemctl restart gateway-services.service` → 期望单元全部 active 并持续 `healthStableSec` → `committed`；
  超时或重启失败 → 恢复备份、删除新建的文件 → `rolled-back` → 再重启服务并记录回退后的健康结果。
- 进行中的事务收到回退请求：服务端写中止标记，助手在下一步（健康检查每秒、重启命令每 200 ms）看到后回退。
- 助手进程死掉（掉电等）：SystemMonitor 每 30 秒检查，没有活着的助手且超过 15 秒没有进展的事务按“中断”回退。
- 生产升级日志管理的运行目录（存在 `data/runtime-production`）**保持现有保护**：正式应用回 409
  `production_runtime_locked`，与 v1 相同；预演、快照照常。
- 可写路径：v1 快照集合里的文件，加上运行目录下 `device_identity.json`、`apps/*.json`、`devices/*.json`、`logic/*.json`
  （没有就新建，回退时删除）；不写符号链接；证书、私钥、信任公钥不在可写范围。快照同样列出运行目录里这些文件。

## 7. 与交接文档的差异（以边端为准）

1. **写点没有“仲裁限值”**：边端现有写入路径对越界值是拒绝，不会改小后采纳；所以 `adoptedValue` 要么等于请求值、要么为 `null`
   （带 `rejectReason`）。`arbitrationLevel` 取 `ems-parameter`（EMS 虚拟参数，本地落盘）或 `device-write`（设备驱动写）。
2. **出厂 EMS 虚拟点里只有计划曲线 400–447 可写**；161 / 455 等参数在点表里 `write.enable=false`，写点预演直接拒绝
   （`point write is disabled`）。这些参数要改，走配置直推。
3. 事务的 `services` 是 `gateway-services.sh list` 的全部期望单元（直推总是整体重启 gateway-services），不是按文件推算的子集。
4. 生产升级日志管理的设备不能现场直推（第 4 节）。
5. 回退进行中的事务回 202（不是 200）+ 当前状态。
