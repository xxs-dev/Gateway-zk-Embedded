## 4. 强制满充

最新版源码定义：

- `29`：强制满充使能。
- `30`：强制满充运行反馈。
- `168/169`：每月两个触发日期，取值范围 1-31。
- `535`：PCS 单相有功上限。
- `1570`：BMS SOC。

旧 `script.cpp` 的实际行为是：整柜处于自动状态、六类普通策略没有运行且当前日命中 `168/169` 时启动；启动后保持到 SOC 达到 100；同一指定日期不重复启动；离开两个指定日期后重新布防。每相目标为 `535 * 2 / 3`，并优先于普通策略。

迁移时做了两项明确的安全修正：

1. 旧源码虽然声明 `29=使能`，触发代码没有读取它。模块化实现必须要求 `29==1`，操作员关闭后本次进入“已完成”状态，同日不会反复启动。
2. 旧源码在强制满充分支中直接返回，绕过后续常规限制。模块化实现只放宽普通 SOC 上限到 100，仍保留单相 P/Q/S 上限、BMS 允许充电功率、台区限制、通讯许可和最终写回总闸。

当前模块图使用 `8/10/12/18/20/22` 的实际运行反馈判断普通策略是否介入，这是对现有模块化运行状态的适配，不复用已被循环策略占用的旧 `17` 地址。状态机使用内部点保存“等待/满充中/本次完成”，服务重启后可从 Graph 状态文件恢复。

### 5.1 现场 Index 冲突适配

通用出厂图保留舜通原始 Index，但现场已有物理点时必须先做全局重复检查，再使用 `-IndexRemapFile` 同步重映射图中所有读写引用和虚拟点。不能删除虚拟点后继续使用冲突 Index，否则计算结果会被路由到物理设备共享内存并覆盖采集 latest。

`COMM202600999`（`192.168.22.16`）当前物理点与舜通语义点存在 7 个冲突，映射文件为 `config/examples/shuntong_ems_comm202600999_index_remap.json`：

| 原 Index | 现场用途 | EMS 目标 Index |
| --- | --- | --- |
| `166` | 液冷机组设定温度 | `800166` |
| `203` | 液冷水泵运行状态 | `800203` |
| `209..211` | 除湿机故障状态 | `800209..800211` |
| `1615..1616` | BMS 今日累计充/放电量 | `801615..801616` |

现场生成时应使用当前已运行的 EMS 虚拟点表作为 `-VirtualSource`，这样可以保留电压合格率等其他模块已经占用的虚拟点。生成器会校验重映射目标唯一，并同时处理基础点、动态新增语义点和图节点引用。

```powershell
.\tools\generate_shuntong_modular_graph.ps1 `
  -VirtualSource .\device_ems_modular_virtual.current.json `
  -IndexRemapFile .\config\examples\shuntong_ems_comm202600999_index_remap.json `
  -Output .\shuntong_ems_modular_graph.site.json `
  -RuntimeOutput .\shuntong_ems_modular_graph.site.json `
  -VirtualOutput .\device_ems_modular_virtual.site.json `
  -RuntimeVirtualOutput .\device_ems_modular_virtual.site.json
```

生成命令：

```powershell

.\tools\generate_shuntong_modular_graph.ps1
```
